🔍 Output Node Inference — Verification Questions for Replit

SECTION 1 — Ground Truth: Does “Output” Exist as a Concept?
	1.	Is there a first-class concept of an “output” node in the data model?
	•	If yes:
	•	Where is it defined (type, enum, meta flag)?
	•	How is it persisted?
	•	If no:
	•	Confirm that “output” is inferred, not declared.
	2.	Can a user explicitly mark a node as an output anywhere in the UI or schema?
	•	If not, confirm that all output detection is AI-inferred or heuristic-based.

⸻

SECTION 2 — How Test Flight Decides a Node “Needs a Follow-Up”
	3.	When Test Flight says “this node should be an output” or “needs follow-up,” what code path determines that?
	•	File(s) and function(s) responsible
	•	Is this logic part of:
	•	diagnostics engine?
	•	heuristics?
	•	post-generation validation?
	4.	What signals are currently used to infer that a node is not a valid terminal node?
	•	Examples:
	•	Node type (process vs decision vs output-like)?
	•	Presence/absence of outgoing edges?
	•	Keywords in node label or description?
	•	Position in the graph (leaf node)?
	•	Semantic analysis of node text?
	5.	Is the inference rule closer to:
	•	“All leaf nodes must be outputs”
	•	OR “Some leaf nodes are allowed if semantics imply completion”
	•	OR “Any process node without a follow-up is suspicious”

Please specify which is true.

⸻

SECTION 3 — Semantic Sophistication (Critical)
	6.	Does the system semantically understand completion vs continuation?
	•	Example:
	•	“Notify user of approval”
	•	“Dashboard created”
	•	“Account setup complete”
	•	Are these treated as valid terminal outcomes without requiring an explicit output node?
	7.	Is there any NLP / semantic classification that distinguishes:
	•	terminal actions (notify, complete, finalize, end)
	•	vs transitional actions (process, validate, check, compute)?
	8.	If a node’s description explicitly states an end condition (e.g. “flow ends here”), is that respected?
	•	Or does Test Flight still require structural continuation?

⸻

SECTION 4 — False Positives & Confusion Cases
	9.	In what situations does Test Flight incorrectly suggest adding follow-up steps?
	•	Known false positives?
	•	Examples from logs?
	10.	Is there a known issue where Test Flight “over-corrects” by encouraging extra nodes even when the workflow is logically complete?
	11.	Are these suggestions repairable today, or do they tend to create churn (more nodes, more confusion)?

⸻

SECTION 5 — Decision Repair Interaction
	12.	Does Decision Repair ever convert a node into a terminal/output-equivalent automatically?

	•	Or does it only fix decisions, not terminal semantics?

	13.	Can Decision Repair mistakenly “repair” a valid terminal node by forcing extra branches or outputs?

⸻

SECTION 6 — Audit & Explainability
	14.	When Test Flight flags “should be an output,” is that reasoning recorded anywhere?

	•	DecisionSnapshot?
	•	diagnostics metadata?
	•	Why Inspector?

	15.	Can we answer: “Why did the system think this node wasn’t a valid end?”

	•	If not, confirm that this is currently opaque.

⸻

SECTION 7 — Design Intent Check (Big Picture)
	16.	Is the current philosophy:

	•	“All workflows must end in explicit output nodes”
	•	OR “Workflows can end naturally if semantics imply completion”

	17.	If the latter is the intent, what safeguards exist to prevent unnecessary output inflation?
	18.	If none exist, confirm that this is a known gap and not user error.
