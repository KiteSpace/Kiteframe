V1 STABILIZATION — IMPLEMENTATION VERIFICATION QUESTIONS

SECTION 1 — SESSION LOCKING (FOUNDATIONAL)

Purpose: Ensure determinism and auditability across proposal/experiment flows.
	1.	Session Creation
	•	Where is the sessionId generated?
	•	Is it created exactly once per:
	•	Propose Solution flow?
	•	Experiment generation flow?
	•	What event clears it (Accept, Cancel, refresh)?
	2.	Router Enforcement
	•	Where in aiRouter.ts is the session lock applied?
	•	Is it enforced before model resolution?
	•	Which taskTypes are locked?
	•	Confirm it applies to workflow_reasoning and workflow_experiments
	•	Confirm it does NOT apply to general_chat
	3.	Settings Immunity
	•	If the user changes model/provider settings mid-session:
	•	Are those changes ignored for the active session?
	•	Are they applied to the next session only?
	4.	Determinism Guarantees
	•	Can Proposed and Alternative ever be generated with different models?
	•	Can experiments in the same batch use different models?
	•	Can regeneration accidentally use a different model?
	5.	Audit Evidence
	•	Where is the locked model recorded?
	•	Is modelUsed, providerUsed, and sessionId captured in DecisionSnapshot?

PASS CRITERIA
	•	One session = one model
	•	No silent model drift
	•	Deterministic replay possible from audit data

SECTION 2 — SEMANTIC VISIBILITY (PHASE 5+)

Purpose: Make AI reasoning legible without changing behavior.
	6.	DecisionSnapshot Coverage
	•	Which semantic fields are currently populated?
	•	heuristicsApplied
	•	decisionRepairs
	•	semanticClaims
	•	unresolvedConcerns
	•	Which are missing or stubbed?
	7.	Repair Transparency
	•	When Decision Repair runs:
	•	Is every fix recorded in the snapshot?
	•	Are repaired decisions identifiable by node ID?
	•	Can we answer “why does this edge exist?”
	8.	WhyInspector Accuracy
	•	Does the inspector clearly separate:
	•	AI-generated intent
	•	Auto-repairs
	•	Unresolved risks?
	•	Are there any semantic claims not surfaced in UI?
	9.	Negative Knowledge
	•	Can the system show:
	•	“This behavior was implied but not structurally enforced”?
	•	Or does it only show what did happen?
	10.	Audit Export
	•	Does exported JSON include:
	•	Semantic claims
	•	Repairs
	•	Model provenance
	•	Session ID
	•	Is export sufficient to reconstruct reasoning offline?

PASS CRITERIA
	•	A human can understand why the workflow looks the way it does
	•	No “magic” changes without explanation

SECTION 3 — DECISION REPAIR (PHASE 6.7)

Purpose: Ensure incomplete decisions are fixed, not re-suggested.
	11.	Detection Accuracy
	•	What exact conditions trigger decision repair?
	•	Does it detect:
	•	Missing Yes/No branches?
	•	Unlabeled decision edges?
	•	Dangling decision edges?
	12.	Repair Scope
	•	Does repair:
	•	Modify existing nodes only?
	•	Reuse node and edge IDs?
	•	Avoid creating parallel workflows?
	13.	Minimalism
	•	Under what conditions is a new node created?
	•	Is there a hard limit of 1 new fallback node?
	14.	Idempotency
	•	If repair runs twice:
	•	Are there zero additional changes the second time?
	•	Have you tested this explicitly?
	15.	Suggestion Suppression
	•	When a decision is repairable:
	•	Are Propose / Experiment options suppressed?
	•	Does Test Flight stop flagging the same issue repeatedly?

PASS CRITERIA
	•	Decision issues converge to zero
	•	No infinite “fix → test → fix again” loop

	17.	Non-Blocking Guarantee
	•	Can loop detection ever:
	•	Fail Test Flight?
	•	Trigger Propose/Experiment automatically?
	•	Modify the workflow?
	18.	Visibility
	•	Where do loop warnings appear?
	•	Inspector?
	•	Insights?
	•	Audit export?
	19.	Feature Flag Behavior
	•	Does disabling the flag:
	•	Fully remove loop warnings?
	•	Leave zero side effects?

PASS CRITERIA
	•	Purely informational
	•	Zero workflow changes
