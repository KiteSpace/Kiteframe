Kiteframe – Replit Task File
Fix Home “Conceptual Workflow” Proposal Updates + Model Routing + Silent Failures + Prevent Duplicate/Append Behavior

Scope
You must fix the homepage → full-screen KiteAI conceptual chat flow BEFORE launch.
This is the “proposal phase” (no project yet). The user can:
1) Submit a prompt
2) See an initial conceptual workflow proposal (nodes/edges)
3) Click “Include edge/fail cases” (or select options) to expand the proposal
4) Accept/reject proposal
5) ONLY AFTER accept: create/build workflow into a project/canvas

Current observed failures (must address all)
F1. “Include edge/fail cases” triggers AI, but proposal does not update and fails silently.
F2. workflow_reasoning is configured to use invalid model name (gpt-5.1). Responses come back empty (responseLength: 0) so parsing fails, no fallback triggers.
F3. INCLUDE_EDGE_CASES handler relies on regex JSON extraction and has no else-case, causing silent no-op.
F4. Later (in-project) AI “adjustments” can duplicate/append workflows due to ambiguous intent defaulting to merge, and decision repair producing “Option A/B/C/D” edge labels.
F5. Feature flags are disabled in some surfaces (useFeatureFlags called outside Provider), meaning guardrails may be off.

Non-negotiable launch requirements
R1. Home proposal phase must never silently fail. If expansion fails, show a clear error and allow retry.
R2. Model routing must use valid models and MUST have robust fallback; never accept empty response as “success”.
R3. Home proposal updates must not rely on brittle regex matching; must parse structured output deterministically.
R4. In-project mutation must never append a second canonical workflow without explicit “replace” confirmation (or only allow patch edits).
R5. Edge repair must never create “Option A/B/C/D” labels.
R6. Feature flag provider must wrap all components using useFeatureFlags; no “all flags disabled” runtime state in normal operation.

PHASE 2 — Replace regex JSON scraping with structured output parsing (home proposal)
Problem: INCLUDE_EDGE_CASES uses regex like:
  expandResponse.text.match(/\{[\s\S]*"nodes"[\s\S]*"edges"[\s\S]*\}/)
and if it fails, nothing happens.

2.1 Define a stable “Proposal” schema
Create types (shared):
type ProposalNode = { id: string; label: string; description?: string; type: "input"|"process"|"condition"|"output"; icon?: string; iconColor?: string; };
type ProposalEdge = { id: string; source: string; target: string; label?: string; };
type WorkflowProposal = { title?: string; summary?: string; nodes: ProposalNode[]; edges: ProposalEdge[]; assumptions?: string[]; };

2.2 Change AI prompt contract for home proposal calls
- For both initial proposal and edge-case expansion calls, instruct model:
  “Return ONLY valid JSON matching WorkflowProposal schema. No markdown. No commentary.”
- Add a “json-only” system wrapper at the router level for proposal tasks.

2.3 Parse deterministically
- Replace regex extraction with:
  - JSON.parse on the response body
  - If parsing fails: attempt a single “repair” pass (optional) OR fallback model OR show error UI
- Never silently ignore parsing failure.

2.4 Add explicit else-case + error UI
If parsing fails:
- Set UI state: proposalError = true
- Show toast or inline banner:
  “Couldn’t update the proposal. Retry.”
- Provide actions: Retry / Copy debug ID
- Include requestId in UI (small text) for debugging.

2.5 Guard against partial proposals
Validate:
- nodes length >= 2
- edges length >= 1
- All edge endpoints exist in nodes
If invalid: treat as failure and show error.

Acceptance criteria
- Clicking “Include edge/fail cases” always results in either:
  A) Updated proposal displayed, OR
  B) Visible error state with retry (no silent failure)

PHASE 4 — In-project mutation safety: stop duplicate/append workflows
This is separate from home proposal, but must be fixed for launch because it creates “crazy workflows.”

4.1 Implement explicit mutation modes in in-project chat
- Default: ADVISE (no mutation)
- APPLY (patch edits)
- REPLACE (full rewrite; requires explicit confirmation)
If you already have modes, enforce them.

4.2 Add “full graph payload” detection
Before applying any mutation payload:
- If incoming nodes >= 8 OR incoming nodes >= 0.6 * currentNodes
  OR incoming duplicates 3+ canonical labels (Build/Release/etc),
  then treat as FULL_GRAPH.
Rules:
- FULL_GRAPH + no explicit REPLACE confirmation => do NOT apply mutation. Return “needs confirmation” UI.
- FULL_GRAPH must never default to merge.

4.3 Patch edits should diff, not append
- Add semanticKey = normalize(label)+":"+type to node meta.
- When mutation includes nodes with matching semanticKey, update existing nodes instead of creating duplicates.

4.4 Replace operation must be atomic + undoable
If user confirms REPLACE:
- Clear existing nodes/edges for that workflow tab
- Insert new graph
- Single history entry
- One-step undo restores previous graph

Acceptance criteria
- In-project “adjustments” cannot create a second parallel copy of the workflow.
- Full rewrites require explicit Replace confirmation.

PHASE 5 — Decision repair: ban “Option A/B/C/D”
5.1 Update runWorkflowRepairs.ts
When repairing decision:UNLABELED_EDGES:

- If you can infer meaningful binary labels with high confidence (>=0.75):

  - “Yes/No”
  - “Sufficient/Insufficient”
Else:
  - Leave labels empty (preferred).
Add a unit test:
- Assert no edge label matches /^Option\s+[A-D]$/i after repairs.

Acceptance criteria
- No “Option” labels appear in any mutated workflows.
