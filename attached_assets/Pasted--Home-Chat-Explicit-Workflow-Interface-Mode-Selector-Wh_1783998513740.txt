# Home Chat — Explicit Workflow / Interface Mode Selector

## What & Why

The home screen’s KiteAI chat currently only knows how to generate
workflows. When a user asks for a UI/dashboard/interface, it generates
design JSON (via the same underlying generation logic proven in the
design editor’s AI panel, task #204) but has no path to do anything
useful with it, so it dumps raw JSON as chat text.

Rather than trying to infer intent from the prompt (keyword heuristics
or a classifier both introduce misdetection risk — e.g. “workflow for
approving UI changes”), the user explicitly selects which thing they
want before submitting. No detection logic, no ambiguity.

## Done looks like

- A mode selector (Workflow / Interface) appears on the home screen,
  above or alongside the chat input.
- **Workflow mode** (existing behavior, unchanged): prompt goes to the
  current KiteAI workflow chat exactly as it works today.
- **Interface mode**: prompt bypasses the chat entirely.
  - On submit, the UI immediately shows a skeleton/loading state — no
    intermediate chat messages, no raw JSON ever shown to the user.
  - The prompt is sent through the same design-generation pipeline
    already used by the design editor’s AI panel (same prompt template,
    same validation against the craft.js schema).
  - On success: a new `designs` row is created with
    `claimed_by_user_id` set to the current logged-in user immediately
    (auto-claimed — this differs from the external skill route, where
    designs are created unclaimed because there’s no user session).
    The user is navigated to the real `/designs/:id`, rendering
    editable.
  - On failure/validation error: an inline error message is shown
    (e.g. “Couldn’t generate that layout — try rephrasing”); the user
    stays on the home screen and can retry. Raw JSON must never reach
    the screen.
- The selected mode **persists** as the user’s last-used preference
  (e.g. stored in user settings or localStorage keyed to the user) and
  is pre-selected the next time they return to the home screen, rather
  than resetting to a default each visit.

## Out of scope

- Any prompt-based inference of intent (keyword matching, classifier
  calls) — explicitly rejected in favor of the explicit selector.
- A correction/undo flow for “I picked the wrong mode” beyond just
  switching the selector and resubmitting — not needed since there’s
  no misdetection to correct.
- Changes to the external Claude Code skill route or its unclaimed/claim
  flow — that path is unaffected by this change.
- A property-editing sidebar or any other design-editor feature — this
  task is scoped to the home screen entry point only.

## Steps

1. **Add the mode selector UI** — segmented control or two buttons
   (Workflow / Interface) on the home screen, above the chat input.
   Reflect the persisted last-used mode as the initial selection.
1. **Persist the selection** — on change, save the selected mode (e.g.
   `lastUsedHomeMode` on the user record, or a `localStorage` key
   scoped to the logged-in user if a full DB round-trip isn’t
   warranted for a single preference). Read it back on page load to
   set the initial selector state.
1. **Wire Workflow mode** — no behavior change; confirm the existing
   KiteAI workflow chat still runs exactly as today when this mode is
   selected.
1. **Wire Interface mode submit handler** — on submit, instead of
   invoking the chat, call the same design-generation function/endpoint
   used by the design editor’s AI panel (task #204’s pipeline). Reuse
   directly — do not fork a second copy of the prompt or validator.
1. **Add the loading/skeleton state** — client-side state shown
   immediately on submit, replaced once generation completes (success
   or failure). No intermediate “generating…” chat bubbles — this is
   a distinct UI, not a chat transcript.
1. **Wire success path** — on valid generated output, create the
   `designs` row with `claimed_by_user_id = req.user.id` and
   `source = 'native'` (or a distinct source value like `'home-ai'` if
   you want to track this entry point separately from manual
   drag-and-drop authoring — pick whichever is more useful for your
   own analytics later). Navigate to `/designs/:id`.
1. **Wire failure path** — on validation failure, show an inline error
   in place of the skeleton, allow retry without losing the entered
   prompt.
1. **Manual test** — submit a UI-ish prompt (e.g. “admin dashboard for
   user management,” the exact case that surfaced this issue) in
   Interface mode and confirm: skeleton shows, no raw JSON ever
   appears, final result lands on `/designs/:id` fully editable, and
   the mode selector still shows “Interface” as selected on next visit
   to the home screen.

## Relevant files
