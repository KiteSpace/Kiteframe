KITEFRAME — UX AUTH + BETA GATING SPEC
Version: 1.0
Audience: Replit Engineering
Status: REQUIRED before public beta

================================================
GOAL
================================================
Create a deterministic, low-confusion authentication + beta access flow that:

• Allows Beta users to sign in with OAuth and enter the app
• Prevents non-Beta users from accessing the app
• Automatically handles users who already have accounts
• Avoids dead ends, silent failures, or ambiguous states
• Keeps UX aligned with Kiteframe’s product positioning (calm, confident, intentional)

This spec assumes:
✓ OAuth session persistence is working
✓ /api/auth/user returns a valid session after login

================================================
CORE PRINCIPLES
================================================
1. Never ask the user “Sign up or Sign in?”
   → OAuth determines identity automatically

2. Never block a signed-in user without explanation

3. Beta gating is *post-auth*, not pre-auth

4. Every state must have a visible, understandable UI

================================================
CANONICAL USER STATES
================================================
These are the ONLY allowed states.

STATE A — UNAUTHENTICATED
--------------------------------
User is not logged in.

UI:
• Landing page (Beta messaging)
• OAuth buttons:
  – Continue with Google
  – Continue with GitHub
  – Continue with Replit
• Email waitlist form (visible below auth options)

Actions:
• OAuth click → redirect to provider
• Email submit → waitlist confirmation

NO access to Home / App routes.

--------------------------------

STATE B — AUTHENTICATING
--------------------------------
OAuth redirect in progress.

UI:
• Full-page loading state
• Copy:
  “Signing you in…”

Notes:
• No user interaction
• No navigation controls

--------------------------------

STATE C — AUTHENTICATED (SESSION CONFIRMED)
--------------------------------
User has a valid session cookie.

System action:
• Call GET /api/auth/user
• Receive user object

Transition:
→ Immediately evaluate beta status

--------------------------------

STATE D — AUTHENTICATED + BETA ACCESS
--------------------------------
User is authenticated AND allowed into beta.

UI:
• Instant redirect to /app (Home / Editor)
• No interstitial screen

Notes:
• This must feel fast and confident
• No extra confirmation steps

--------------------------------

STATE E — AUTHENTICATED BUT NOT IN BETA
--------------------------------
User has a valid account but is not beta-approved.

UI: WAITLIST DASHBOARD

Required content:
• Message:
  “You’re signed in, but Kiteframe is currently in private beta.”
• Show signed-in email
• Beta status indicator:
  – Pending
  – Approved (future)
• Email field:
  – Pre-filled
  – Editable
• CTA:
  “Request Beta Access”
• Secondary CTA:
  “Sign out”

Actions:
• Submitting email updates waitlist record
• Does NOT log user out

--------------------------------

STATE F — AUTHENTICATED + PREVIOUSLY WAITLISTED
--------------------------------
User already exists in waitlist table.

UI:
• Same as STATE E
• Show:
  “We already have your request — you’ll hear from us.”

--------------------------------

================================================
EDGE CASE HANDLING
================================================

CASE 1 — User thinks they are new, but account exists
-----------------------------------------------------
Behavior:
• Silent account linking by email
• User is logged in automatically
• No messaging about “existing account”

CASE 2 — User signs in with different providers
-----------------------------------------------------
Behavior:
• Providers auto-link by email
• Single canonical user ID

CASE 3 — OAuth succeeds but beta check fails
-----------------------------------------------------
Behavior:
• Never return to Sign In page
• Always land in WAITLIST DASHBOARD

CASE 4 — OAuth failure
-----------------------------------------------------
UI:
• Inline error message
• Retry same provider
• Offer alternate providers

================================================
ROUTING RULES (STRICT)
================================================

/                → Landing (STATE A)
/signin          → Landing (STATE A)
/app             → Requires STATE D
/waitlist        → Requires STATE E or F

Unauthorized access to /app:
• Redirect to Landing
• Preserve intended route in memory

================================================
API CONTRACTS
================================================

GET /api/auth/user
Returns:
• 200 + user object → authenticated
• 401 → unauthenticated

User object MUST include:
{
  id,
  email,
  isBeta: boolean,
  waitlistStatus?: 'pending' | 'approved'
}

================================================
VISUAL / UX NOTES
================================================

• No modals for auth or beta gating
• All transitions are page-level or inline
• Never refresh the page on state change
• Avoid auth loops at all costs

================================================
NON-GOALS (DO NOT IMPLEMENT)
================================================

• No Auth0
• No magic links
• No invite codes (yet)
• No role selection
• No pricing tiers

================================================
SUCCESS CRITERIA
================================================

✓ A Beta user can sign in and reach /app in one flow
✓ A non-Beta user never reaches /app
✓ No OAuth button leads to a blank refresh
✓ No user is unsure whether they are signed in
✓ Waitlist users always have a visible status
