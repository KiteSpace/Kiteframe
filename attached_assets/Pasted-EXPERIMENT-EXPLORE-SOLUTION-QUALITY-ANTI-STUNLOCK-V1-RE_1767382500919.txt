EXPERIMENT & EXPLORE — SOLUTION QUALITY + ANTI-STUNLOCK (V1)
REPLIT IMPLEMENTATION INSTRUCTIONS

OBJECTIVE

Improve the usefulness and decisiveness of Explore and Experiment outputs by:

reducing choice overload

forcing solution-oriented proposals

increasing AI confidence and clarity

preventing vague or brainstorming-style responses

This task is behavioral and UX-focused, not architectural.

NON-NEGOTIABLE PRINCIPLES

Explore is system-initiated and solution-oriented, not ideation

Experiment is user-initiated and exploratory

Fewer, clearer options are always better than many vague ones

The AI must recommend a path, not just list possibilities

Forward momentum > optional discussion

PART 1 — EXPLORE OBJECT (CRITICAL FIXES)

1.1 Limit the number of suggestions

Explore must generate:

Exactly 1 primary (recommended) solution

At most 1 alternative solution

Never more than 2 total solution paths

If the AI would otherwise propose more, it must internally rank and discard the rest.

FAILURE CONDITION:
More than 2 solution paths shown in Explore.

1.2 Force a “recommended solution” structure

Explore output MUST follow this structure:

Recommended approach (required)

Alternative approach (optional, only if meaningfully different)

The recommended approach must be clearly labeled as such.

The AI must not ask the user to choose between equal options.

1.3 Enforce solution-oriented language

Each solution must describe a concrete structural change, not a theme.

Each proposal must explicitly state:

What changes in the workflow

Where the change happens (node / step / branch)

What new path, condition, or node is introduced

Examples of DISALLOWED language:

“Improve validation”

“Enhance the UX”

“Add better handling”

“Consider introducing…”

Examples of REQUIRED language:

“Insert a conditional branch after X that routes Y failures to Z”

“Add a retry path from node A to node B”

“Split the flow at step C based on condition D”

FAILURE CONDITION:
Solutions that do not map to concrete workflow changes.

1.4 Reduce follow-up affordances in Explore

Explore must NOT end with open-ended questions like:

“What would you like to do?”

“Do you want to explore further?”

Explore must surface:

One primary action (e.g. “Apply solution” / “Create branch”)

No more than one secondary escape hatch (e.g. “Discuss further” — informational only)

Default emphasis must be on applying the recommendation.

1.5 Tone and confidence

Explore copy should:

Be assertive

Avoid hedging (“could”, “might”, “consider”)

Sound like a proposal, not a brainstorm

Mental model:

“Here is the best way to address this issue.”

PART 2 — EXPERIMENT OBJECT (BOUNDARIES ONLY)

2.1 Experiment remains user-directed

Experiment header options remain:

What If

Enhancement

Wildcard (open prompt)

Experiment outputs may:

Be exploratory

Offer multiple ideas

Ask follow-up questions

Do NOT apply Explore constraints (recommendation, limits) to Experiment.

PART 3 — VISUAL & UX DIFFERENTIATION (GUARDRAILS)

3.1 Layout vs styling

Experiment and Explore may share layout and container structure

Styling must differ to signal intent:

Experiment = neutral / exploratory

Explore = directive / system-identified

This task does NOT require new UI components, only enforcement of behavioral difference.

PART 4 — QUALITY GATE (INTERNAL CHECK)

Before rendering an Explore response, enforce the following checks:

Does the output contain a clearly labeled Recommended approach?

Are there ≤ 2 solution paths total?

Does each solution describe a concrete workflow change?

Is the language decisive and non-hedging?

If any check fails:

Regenerate the response with stricter constraints

Do NOT fall back to vague output

PART 5 — EXPLICIT NON-GOALS (DO NOT IMPLEMENT)

Do NOT add conversational chat handoff from Explore (future release)

Do NOT add more options to “help the user decide”

Do NOT reintroduce brainstorming language

Do NOT expose internal reasoning or ranking

ACCEPTANCE CHECKLIST (MUST PASS)

Explore outputs never exceed 2 solutions

One solution is always explicitly recommended

Solutions are concrete and workflow-specific

Users are not asked to decide between many options

Experiment behavior remains unchanged

END OF INSTRUCTIONS
