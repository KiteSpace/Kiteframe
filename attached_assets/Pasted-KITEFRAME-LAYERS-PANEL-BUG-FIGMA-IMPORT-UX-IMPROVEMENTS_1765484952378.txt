KITEFRAME — LAYERS PANEL BUG + FIGMA IMPORT UX IMPROVEMENTS
===========================================================

GOALS
-----
1) FIX BUG: Layers panel shows workflows from the wrong project.
2) FIX UX: Figma import should:
   - Let users choose frames BEFORE project creation.
   - Never silently generate workflows.
   - Let users choose how "Generate workflow" behaves AFTER import.

All work should respect the current architecture:
- Global stores exist (CollapseStore, VLStore, workflowNameStore, nodeToWorkflowStore).
- FlowDetection + graphWorker exist and run automatically when nodes/edges change.
- Figma import currently creates only image nodes with figmaSemantic (no auto workflows).


===========================================================
PART 1 — FIX CROSS-PROJECT LAYERS PANEL STATE LEAKAGE
===========================================================

ROOT CAUSE
----------
- Collapse/visibility/lock/workflow mappings are stored in **global singletons**:
  - 'layers-collapsed-state'
  - VLStore (visibility/lock)
  - workflowNames
  - nodeToWorkflowStore
- These stores are NOT scoped by projectId.
- Layer grouping (via graphWorker + FlowDetection) is cached or reused across projects.
- When switching projects, old state is reused and displayed against a new canvas.

DESIRED BEHAVIOR
----------------
- Layers panel state MUST be **per-project**.
- When switching projects:
  - All workflow groupings, collapse state, visibility, and names must reset or be loaded from the appropriate project-specific storage.
  - No workflows/nodes from another project should appear.

IMPLEMENTATION TASKS
--------------------

1. Pass projectId into LayersPanel
   - In workflow-editor.tsx (or parent), ensure the current projectId is passed as a prop to LayersPanel.
   - Example: <LayersPanel projectId={project.id} ... />

2. Project-scope all Layers-related stores
   - For each of:
     - CollapseStore
     - VLStore (visibility + lock)
     - workflowNameStore
     - nodeToWorkflowStore
   - Change the internal structure to be keyed by projectId.
   - Example pattern (conceptual):

     const collapseState = {
       [projectId]: {
         [workflowId]: {...}
       }
     };

3. Update localStorage keys to include projectId
   - Current: 'layers-collapsed-state'
   - New:    'layers-collapsed-state-' + projectId
   - Similarly for visibility/lock state and workflow names, if persisted.

4. Reset nodeToWorkflowStore on project switch
   - When projectId changes:
     - Clear existing nodeToWorkflow mappings.
     - Re-run graphWorker + FlowDetection only for the current project's nodes/edges.
   - Option:
     - Introduce resetLayersState(projectId) function:
       - Clears internal caches
       - Loads/pulls correct per-project state (if any)

5. Ensure FlowDetection only uses current project graph
   - Verify that FlowDetection.detectFlows() is always called with the current canvas nodes/edges and nothing cached from a previous project.
   - If graphWorker uses any global caches, those must be keyed by projectId or reset on project load.

6. Regression behavior:
   - Switch between Project A and Project B:
     - Confirm workflows shown in Layers always match each project’s own nodes/edges.
     - Confirm collapse/visibility/lock states do not leak between projects.


===========================================================
PART 2 — FIGMA IMPORT UX: FRAME SELECTION + NO AUTO WORKFLOWS
===========================================================

CURRENT BEHAVIOR (as observed)
------------------------------
- User creates a project and uses Figma import.
- Project is created.
- An image node representing the Figma frame is added.
- Layers panel shows "random" workflow groups populated with node IDs + edges.
- This feels like workflows are being auto-generated from Figma import.

Actual behavior from code:
- convertFigmaFrameToNodes() and convertMultipleFramesToNodes() only create image nodes and empty edges.
- generateWorkflowFromFigmaImageNode() is the **only** function that generates workflows.
- The Layers bug (Part 1) makes it appear like workflows are being auto-created.

We want to:
1) Make the UX explicit: no workflow generation on import.
2) Give user control over which frames become workflows.

-----------------------------------
PART 2A — FRAME SELECTION PRE-PROJECT
-----------------------------------

DESIRED FLOW
------------
1. User selects "Create project from Figma file" (or similar).
2. After OAuth/PAT + file selection:
   - Show a FigmaFramePicker grid/list of frames in the file.
3. FigmaFramePicker UI:
   - Shows frames as thumbnails or rows.
   - Allows:
     - Select all
     - Select none
     - Individual checkbox selection
4. On continue:
   - Only selected frames are imported as image nodes.
   - NO workflows are generated.
   - NO edges are created.
5. The new project opens with:
   - Canvas containing only the selected Figma image nodes.
   - Layers showing just these nodes (no workflow groups beyond what FlowDetection detects from existing edges — which should be none).

IMPLEMENTATION TASKS
--------------------

1. Audit FigmaImportModal/FigmaFramePicker
   - Confirm if the FigmaFramePicker already supports:
     - Displaying multiple frames
     - Multi-select state
   - If it already does, ensure ONLY selected frames are passed to onImport.
   - If not, implement:
     - `selectedFrameIds` state
     - "Select All" / "Select None" buttons
     - Checkbox per frame

2. Ensure project creation uses only selected frames
   - In the code path that creates a project from Figma:
     - When onImport(framesWithSemantics) is called,
       use only the selected frames to:
       - create image nodes
       - attach figmaSemantic
       - store figmaFileKey and figmaId in node.data

3. Explicitly DO NOT call generateWorkflowFromFigmaImageNode() during import
   - Verify that no code path calls this during initial Figma import.
   - Add comments in the code to make this contract obvious:
     - "Figma import is reference-only; workflows are created explicitly via toolbar actions."

--------------------------------------------
PART 2B — POST-IMPORT "GENERATE WORKFLOW" UX
--------------------------------------------

DESIRED FLOW
------------
After the project + Figma frames exist:

- User sees an image node(s) representing Figma frames.
- User can:
  - Right-click → "Generate workflow from this frame"
  - Multi-select frames and use toolbar → "Generate workflow"
  - Choose whether to:
    - Generate from all imported frames
    - Generate from selected frames only

IMPLEMENTATION TASKS
--------------------

1. Toolbar design (top or contextual toolbar)
   - Add a "Generate Workflow" button that is active when:
     - At least one image node with node.data.figmaSemantic is present.

2. Button behavior:
   a) Default click:
      - If multiple image nodes are selected, generate workflow from selected frames.
      - If none are selected, show a popover or small modal to choose:
         - "Use all Figma frames in this project"
         - "Cancel" or "Select frames manually"

   b) Optional: Split button behavior:
      - Primary action: "Generate from selected"
      - Secondary (chevron): menu with:
         - "Generate from selected frames"
         - "Generate from all imported frames"

3. Integrate with generateWorkflowFromFigmaImageNode()
   - Refactor this into a more general function:
     - generateWorkflowFromFigmaNodes(nodes: Node[])
   - When called:
     - Use figmaSemantic.workflowGraph for each node.
     - Apply ordering rules if multiple frames (separate spec).
     - Create workflow nodes + edges.
     - Wrap in UndoRedoManager batch/transaction so it’s undoable.

4. Ensure reference frames are excluded
   - If node.data.isReferenceFrame === true:
     - Exclude that node from candidate frames for workflow generation.
   - This will be especially important once isReferenceFrame is implemented.

5. Confirm Layers behavior post-generation
   - After new nodes/edges are generated:
     - FlowDetection should create new workflow groups only for the generated workflows.
     - Layers should reflect the new workflows for the **current** project only (after Part 1 fixes).

-----------------------------------------
PART 2C — UX CONSISTENCY / COMMUNICATION
-----------------------------------------

1. Copy guidance:
   - Figma import UX should clearly say:
     - "Imported frames are added as reference images. You can generate workflows from them later using the toolbar."
   - Tooltip on "Generate Workflow" button:
     - "Turn selected Figma frames into a workflow."

2. No hidden/automatic behaviors:
   - All workflow generation from Figma must be tied to explicit user actions (context menu, toolbar button).
   - No auto workflows on:
     - Import
     - Project creation
     - Project load
