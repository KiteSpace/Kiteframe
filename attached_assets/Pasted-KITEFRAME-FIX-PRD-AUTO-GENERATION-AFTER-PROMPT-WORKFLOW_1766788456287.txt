KITEFRAME — FIX PRD AUTO-GENERATION AFTER PROMPT WORKFLOW (PROJECT ID RACE)

SUMMARY (CONFIRMED)
PRD generation and save functions run, but the PRD is saved under the wrong projectId due to a race condition:
- generateWorkflowDirectly() tries to derive effectiveProjectId via tabs.find(tabId)
- Immediately after createBlankTab(), setTabs() has not committed yet, so tabs.find(...) returns undefined
- Fallback projectUuid from route params may be undefined or not equal to the new tab’s UUID
- PRD is persisted under prd-workflow-${wrongProjectId}-${workflowId}
- ProjectPanel later loads using activeTab.projectUuid (correct) and cannot find the saved PRD

GOAL
Make PRD save/load keys stable and identical by ensuring generateWorkflowDirectly() receives the correct projectId at call time (no lookup via async React state).

----------------------------------------------------------------------------------------------------
PART 1 — REQUIRED CODE CHANGE (NO GUESSING)
Change the call chain so generateWorkflowDirectly receives projectId explicitly.

A) In workflow-editor.tsx (or where new tab is created before calling generateWorkflowDirectly)
1) When creating the new tab, you already have newTab.projectUuid (or equivalent).
2) Pass it directly into generateWorkflowDirectly.

BEFORE (current pattern)
generateWorkflowDirectly(prompt, newTab.id, generatePRD);

AFTER (fix)
generateWorkflowDirectly({
  prompt,
  tabId: newTab.id,
  generatePRDFlag: generatePRD,
  projectId: newTab.projectUuid,     // REQUIRED
  cloudProjectId: newTab.cloudProjectId, // OPTIONAL if used anywhere in storage keys
});

B) Update generateWorkflowDirectly signature to accept an object
In workflow-editor.tsx:
- Replace function signature:
  async function generateWorkflowDirectly(prompt, tabId, generatePRDFlag) { ... }

With:
  type GenerateWorkflowDirectlyArgs = {
    prompt: string;
    tabId: string;
    generatePRDFlag: boolean;
    projectId: string;              // REQUIRED — must be stable
    cloudProjectId?: string | number; // OPTIONAL
  };

  async function generateWorkflowDirectly(args: GenerateWorkflowDirectlyArgs) {
    const { prompt, tabId, generatePRDFlag, projectId } = args;

    // HARD RULE:
    // Do not call tabs.find(...) to derive projectId.
    // projectId MUST come from args.projectId.
  }

C) Remove / disable the unstable projectId resolution logic
Delete or bypass:
  const currentTabData = tabs.find((t) => t.id === tabId);
  const effectiveProjectId = currentTabData?.projectUuid || projectUuid;

Replace with:
  const effectiveProjectId = projectId;

If projectUuid from route params is needed for legacy flows, ONLY use it when projectId is missing.
But per this fix, projectId should never be missing for prompt-based creation.

PART 2 — ENSURE PRD SAVE USES THE SAME IDs AS UI LOAD
A) Confirm the save call uses:
- projectId: effectiveProjectId (now stable from args.projectId)
- workflowId: workflowGroupId (whatever is used consistently by FlowDetection & display)
Example:

B) Confirm the read path uses the exact same:

C) Confirm ProjectPanel passes projectId === activeTab.projectUuid (preferred)
If ProjectPanel falls back to activeTabId, only do so if there is no projectUuid.
For prompt-based creation, projectUuid MUST exist.
