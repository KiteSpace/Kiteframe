# External Design API — Routes, Fixes, and Verification Needed

## Context

The Claude Code design-generation skill (mirroring the existing
`kiteframe-brainstorm` workflow skill) cannot be built yet. The
skill's draft `SKILL.md` references two routes that don't exist, and
depends on an unauthenticated/unclaimed write path that has no
equivalent for the new craft.js design format. This ticket covers what
needs to be built and verified before the skill files can be written
against a real, working API.

This is API/backend work only — no changes to the design editor, the
home chat, or any in-app UI are needed for this ticket.

---

## Part 1 — Build: unauthenticated external write route

**Route:** `POST /api/external/designs`

Does not exist today. The only creation route is `POST /api/designs`,
which requires auth and immediately sets `claimedByUserId` — wrong
shape for a Claude Code skill call, which has no user session.

**Requirements:**
- Auth via the existing scoped API key middleware (`requireApiKey`),
  same as the workflow skill's external routes — not user session auth.
- Rate-limited using the existing per-key limiter pattern
  (`externalApiLimiter` or equivalent).
- On success: creates a row in the `designs` table with:
  - `claimed_by_user_id: null` (unclaimed — the whole point of this
    route existing separately from `POST /api/designs`)
  - `source: 'skill'`
  - `api_key_id`: the calling key's id
  - `craft_state`: the submitted tree JSON
- **Validation must match `POST /api/designs`'s server-side strictness
  exactly** — same `validateCraftState()` logic (ROOT exists,
  `resolvedName` in `SERVER_ALLOWED_CRAFT_COMPONENTS`, parent/child
  reference integrity, no cycles). Do not write a separate, looser
  validator for this route — reuse the existing function.
- **Response shape:** `{ "id": "<uuid>", "url": "/designs/<uuid>" }` —
  no `expires_at` field. (The draft skill docs incorrectly show
  `expires_at`, which belongs to the unrelated legacy
  `POST /api/designs/generate` route — confirm this ticket's version
  does not include it.)

**Verify after building:**
- A request with a valid craft.js tree returns 200 + the id/url shape above.
- A request with an invalid `resolvedName` (something not in the
  enum) returns 422, not a silent save.
- A request with a broken parent reference or a cycle returns 422.
- The created row has `claimed_by_user_id = null` and is visible via
  the existing `GET /api/designs/:id` (unauthenticated read already
  works — confirm the new rows are readable through it with no changes
  needed there).
- The existing claim flow (`POST /api/designs/:id/claim`) works
  unmodified against a design created through this new route — i.e.
  confirm claiming doesn't assume `source: 'native'` anywhere.

## Part 2 — Build: prompt-template route

**Route:** `GET /api/external/designs/prompt-template`

Does not exist today. Mirrors the already-working
`GET /api/external/workflows/prompt-template`.

**Requirements:**
- Auth via the same API key middleware, same rate limiter.
- No AI/model call happens here — this is a static/config response,
  same principle as the workflow version.
- Response shape:
  ```json
  {
    "version": "1.0.0",
    "system_prompt": "<the design system prompt>",
    "output_schema": { /* JSON-schema-shaped description of the craft.js tree format */ },
    "few_shot_examples": [ /* description -> craft_state tree pairs */ ]
  }
  ```
- `system_prompt` should be adapted from the existing
  `server/lib/designPrompt.ts`, but:
  - **Fixed to remove `AstryxImage`** (see Part 3 — this component is
    referenced in the current prompt but not server-allowed; don't
    propagate that bug into the skill's version).
  - **Must state the mandatory tree structure explicitly**: `ROOT`
    (always `AstryxSection`) → one or more `AstryxArtboard` nodes
    (representing distinct screens) → component trees nested inside
    each artboard. This structural rule isn't optional and should be
    stated as a hard requirement, not just implied by the component
    list.
  - **Must state `AstryxCard` is a leaf** in generated JSON (no
    children), even though the editor's drag-and-drop rules allow
    dropping into it — the skill's few-shot examples and instructions
    should not show components nested inside a Card.
- `output_schema` should reflect the exact node shape from
  `designSchema.ts`: `type.resolvedName`, `props`, `parent`, `nodes`,
  `linkedNodes` as required fields, plus the full
  `SERVER_ALLOWED_CRAFT_COMPONENTS` enum for `resolvedName`.
- `few_shot_examples`: at least 1-2 examples showing a realistic
  multi-artboard design (not just a single flat component list) so the
  model sees the artboard-as-screen pattern demonstrated, not just
  described in prose.

**Verify after building:**
- A GET request with a valid API key returns all three fields with
  non-empty content.
- The returned `output_schema`'s enum matches
  `SERVER_ALLOWED_CRAFT_COMPONENTS` exactly (no drift between what this
  route advertises and what `POST /api/external/designs` actually
  accepts) — this is worth a direct diff, not just a visual check,
  since keeping these two in sync by hand is the most likely place for
  future bugs to creep in.

## Part 3 — Fix: `AstryxImage` prompt/allowlist mismatch

Independent bug, unrelated to the skill, but should be fixed as part
of this pass since the design skill's prompt is being written now and
shouldn't inherit it.

**The problem:** `server/lib/designPrompt.ts` (the existing in-app AI
generation prompt) lists `AstryxImage` with props `{ src, alt, width,
height }`, but this component is absent from
`SERVER_ALLOWED_CRAFT_COMPONENTS` in `designSchema.ts` and absent from
the resolver in `resolver.tsx`. If the model ever generates it (in the
home chat, the design editor's AI panel, or eventually the skill), the
server correctly rejects with 422 — but the user just sees a failure
with no clear reason, since the prompt told the model this was a valid
option.

**Two ways to resolve — pick one:**
- **Remove `AstryxImage` from `designPrompt.ts`** if there's no real
  image component built yet. Simplest, no new component work.
- **Add `AstryxImage` to the resolver and server allowlist** if you
  actually want image support in designs. More work, but closes a real
  gap in the component library rather than just hiding it.

**Verify after fixing:**
- Generate a design (via whichever in-app path is easiest to test)
  with a prompt likely to request an image (e.g. "a product page with
  a hero image") several times, and confirm no 422s occur from this
  specific mismatch.
- If removed: confirm `AstryxImage` no longer appears anywhere in
  `designPrompt.ts`.
- If added: confirm it appears consistently in all three places
  (prompt, resolver, server allowlist) with matching prop shapes.
