SECTION 1 — FIX FILE-LEVEL IMPORT (Figma 400 "Request too large")
================================================================================

Problem
-------
FILE imports (links without node-id) are failing with:

  { "status": 400, "err": "Request too large. If applicable, filter by query params." }

Reason: 
  GET /v1/files/{fileKey} with no depth parameter is too large for complex files.

Solution
--------
Use Figma's depth parameter to reduce payload size:

  GET /v1/files/{fileKey}?depth=1

This returns page/frame structure without deep node trees and is sufficient for:
- page listing
- frame enumeration
- driving the selection UI.

Step 1 — Update fetchFigmaFile
------------------------------

File: client/src/lib/integration/figmaApi.ts

1) Locate fetchFigmaFile. It likely looks like:

   export async function fetchFigmaFile(fileKey: string, patToken?: string) {
     return callFigmaApi(`files/${fileKey}`, patToken);
   }

2) Replace it with:

   export async function fetchFigmaFile(
     fileKey: string,
     patToken?: string,
     depth: number = 1
   ) {
     // Use depth=1 by default to avoid "Request too large" errors on big files.
     return callFigmaApi(`files/${fileKey}?depth=${depth}`, patToken);
   }

3) Update all call sites:

   - For normal usage:
       fetchFigmaFile(fileKey, tokenToUse)
     Do NOT pass depth unless there is a specific, documented reason.

   - This ensures FILE URL imports use depth=1 by default.

Step 2 — No extra error logic needed
------------------------------------

File: client/src/components/modals/FigmaImportModal.tsx

You already have a try/catch around fetchFigmaFile for FILE URLs.
Once depth=1 is in place, the 400 size error should stop occurring.

No new error-handling behavior is required beyond the existing:
- console.error
- user-facing error message

SECTION 2 — CONFIRM URL TYPE HANDLING (FRAME / PAGE / FILE)
================================================================================

Goal
----
Ensure URL handling remains:

- FRAME URL → direct import of one node
- PAGE URL → options, then optional frame selection
- FILE URL → options, then multi-frame flow

Behavior (for reference, NOT a rewrite)
---------------------------------------

FILE: client/src/lib/integration/figmaUrl.ts
FILE: client/src/components/modals/FigmaImportModal.tsx

1) FRAME URL
   - URL includes node-id.
   - Figma node resolves to type FRAME or SECTION (or other frame-like).
   - Behavior:
     - No multi-step selection screens.
     - Direct import: create a single image node.
     - onImport called with a single frame entry.
     - NO workflow generated automatically.

2) PAGE URL
   - URL includes node-id.
   - Figma node resolves to type CANVAS.
   - Behavior:
     - Show "page-options" step:
        - Option 1: "Import as single image"
        - Option 2: "Select individual frames from this page"
     - If "Import as single image":
        - Use images endpoint to get PAGE thumbnail.
        - Create 1 image node representing entire page.
     - If "Select frames":
        - Discover frames under that page.
        - Show FigmaFramePicker with those frames only.
        - onSelect → import ONLY selected frames as nodes.

3) FILE URL
   - No node-id in URL.
   - Behavior:
     - Show a "file-options" step:
       - Option 1 (default): "Select individual frames"
       - Option 2: "Import a page as a single image"
     - Option 1:
       - Call fetchFigmaFile(fileKey, tokenToUse) (now depth=1).
       - Use discoverFrames(fileData) to enumerate frames across pages.
       - Show FigmaFramePicker for those frames (grouped by page if implemented).
     - Option 2:
       - Show page-selection UI.
       - User selects a single page.
       - Use images endpoint to fetch a flattened page image.
       - Create 1 image node for that page.

INSTRUCTIONS:
- Do NOT change working FRAME/PAGE behavior.
- Add the FILE fix via depth=1 as described in Section 1.
- If FILE behavior already matches this description once depth=1 is in place, no further changes are needed.

SECTION 6 — WORKFLOW GENERATOR: SEMANTIC USAGE + HISTORY-BASED UNDO
================================================================================

Goal
----
Align the generator with Kiteframe’s existing history/undo model, without introducing a new undo abstraction.

Files:
- client/src/lib/kiteframe/semanticWorkflowGenerator.ts
- client/src/pages/workflow-editor.tsx

Part 1 — Semantic data usage (VERIFY)
-------------------------------------

In semanticWorkflowGenerator.ts:

- Confirm that semantic is read from:

    const semantic = sourceImageNode.data?.figmaSemantic;

- Confirm that it uses semantic.workflowGraph (or similar) to derive:
  - steps → nodes
  - edges → edge list

- If there is any fallback that generates "dummy" nodes without semantic basis, ensure this fallback is:
  - Clearly separated, or
  - Disabled by default for Figma-based generation.

No major rewrites needed here; this is mainly a sanity check.

Part 2 — History-based undo for workflow generation
---------------------------------------------------

In workflow-editor.tsx (or wherever "Generate Workflow" is executed):

- The app currently uses a history mechanism (e.g., saveToHistory() or similar).

Required behavior:
- Generating a workflow from a Figma frame should result in a **single undoable step** that:
  - Removes all generated workflow nodes and edges.
  - Does NOT remove:
    - Figma reference image nodes
    - Other, pre-existing workflows.

Implementation pattern:
- Immediately before creating nodes/edges, call your existing history snapshot function, e.g.:

    saveToHistory("Generate workflow from Figma");

- Then:
    - Insert all generated nodes.
    - Insert all generated edges.
    - Update any relevant "workflow grouping" metadata (if applicable).

- Do NOT interleave other history points inside the generation routine.

If your history manager supports grouping/batching directly:

- Use it to wrap the entire generation action.
- Name the operation clearly ("Generate workflow from Figma").

If it does NOT support grouping beyond a single snapshot:

- Take one snapshot BEFORE modifications.
- Then perform all modifications synchronously within that logical block.

Acceptance:
- Pressing Undo immediately after generation should revert canvas to the exact state it was in before generation, with:
  - Figma image nodes still present.
  - No residual workflow nodes/edges created as part of generation.

Location:

Suggested incremental improvements:
-----------------------------------

1) Label + input pairing:
   - When semantic metadata indicates an INPUT with a nearby LABEL (or label-like text),
     create a single logical "field" node instead of two disconnected steps.

   - Do not create nodes for elements tagged as:
     - dividers,
     - background containers with no interactive descendants,
     - decorative icons.

   - Avoid creating multiple nodes that represent the same logical action or element

4) Basic layout:
   - After nodes are created, apply a simple horizontal or vertical flow layout
     so the resulting workflow is readable by default and not tangled.

Keep changes modest and deterministic. No ML or heavy inference — just heuristics over the existing semantic model.
