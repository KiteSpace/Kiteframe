Kiteframe Wild Card Node — Architecture & Implementation Clarification Questions

PURPOSE

These questions must be answered before writing implementation instructions for the Wild Card node feature.
The goal is to ensure correct system integration, avoid speculative assumptions, and produce an implementation that is consistent with Kiteframe’s existing canvas, AI, undo/redo, and PRD systems.

⸻

SECTION 1 — NODE TYPE & DATA MODEL
	1.	Where are node types defined and registered today?
	•	Is this via NodeFactory, nodeRegistry, or another abstraction?
	•	What exact files must be modified to introduce a new core node type?
	2.	What is the minimum data schema required for a new node type?
	•	Required fields (id, type, data, position, width, height)?
	•	Are there required defaults enforced anywhere?
	3.	Can nodes store mode-specific metadata?
	•	Example: mode: 'what-if' | 'risk' | 'exploration' | 'enhancement'
	•	Is node data flexible enough for this without breaking serialization, export, or undo?
	4.	Are there any assumptions in the codebase that all nodes are “committed” workflow nodes?
	•	For example: PRD generation, maturity scoring, export, or validation logic
