1. Figma OAuth flow

Answer: Redirect is acceptable, but the initiation must be inline.

Recommended behavior:
	•	The OAuth initiation UI lives inline inside the expanded prompt panel.
	•	If the user is not authenticated, show:
	•	“Connect Figma” inline CTA
	•	Short explanatory text (“We’ll redirect you to Figma to authorize access”)
	•	Clicking “Connect Figma” may redirect (OAuth reality is fine here).
	•	After redirect + successful auth:
	•	Return user to the homepage
	•	Restore PromptContext
	•	Resume the inline Figma URL panel automatically

Why this is correct:
	•	OAuth requires navigation — pretending otherwise causes fragile hacks.
	•	Inline initiation preserves the “no modal interruption” principle.
	•	Restoring state post-redirect avoids user confusion and feels polished.

Explicit non-goal:
Do not embed OAuth in iframes or popups — too brittle.

2. Error states (invalid Figma URL, upload failure)

Answer: Inline errors for attachment-specific failures, toast only for global/system errors.

Rules:
	•	Attachment-specific errors (invalid Figma URL, failed image processing):
	•	Render inline within the attachment slot
	•	Show error state where the attachment would appear
	•	Include:
	•	Error message (human-readable)
	•	Retry action
	•	Remove action
	•	Global/system errors (network down, auth expired unexpectedly):
	•	Toast notification is acceptable

Why:
	•	Inline errors preserve context (“this thing failed”).
	•	Toasts for local failures feel disconnected and frustrating.
	•	This also scales cleanly to multiple attachments.

⸻

3. Attachment limits

Answer: Yes — soft limits, not hard stops.

Recommended limits (MVP):
	•	Max attachments before Send:
	•	1 Figma file
	•	Up to 3 images
	•	Enforce as soft limits:
	•	Disable additional buttons
	•	Show inline helper text:
“You can add more after the project is created.”

Why:
	•	Prevents performance cliffs and prompt bloat.
	•	Keeps the pre-project context focused.
	•	Avoids premature optimization around context length handling.

Important:
Do not silently truncate or ignore attachments.

⸻

4. Quick actions after attachment

Answer: They should remain, but visually de-emphasized.

Behavior:
	•	Keep “Import Figma Design” / “Upload Image” visible
	•	After one Figma attachment exists:
	•	Disable the Figma button (with tooltip explaining why)
	•	Image upload remains enabled until limit is reached

Why:
	•	Removing buttons causes UI jitter and cognitive load.
	•	Disabled-with-reason is clearer than disappearance.
	•	Users understand constraints without feeling blocked.

5. Concern: Figma fetch latency before Send

Answer: Split the fetch into two phases. This is critical.

Phase 1 — Pre-Send (Lightweight, required)

Triggered immediately when user confirms the Figma URL.

Fetch ONLY:
	•	File name
	•	File ID
	•	Thumbnail (if cheap / cached)
	•	Page list (optional, lightweight)

Show:
	•	Attachment card with:
	•	Loading spinner → resolved preview
	•	“Design added” confirmation

NO semantic extraction
NO MCP-heavy analysis
NO AI calls

Phase 2 — Post-Send (Heavy, gated)

Triggered ONLY after user clicks Send.

Do:
	•	Full semantic extraction
	•	Vision / MCP analysis
	•	Workflow inference
	•	Confidence scoring

Why this split is non-negotiable:
	•	Keeps homepage fast and responsive
	•	Avoids wasted computation if user cancels
	•	Matches your desired “set the scene, then commit” mental model
	•	Aligns with ChatGPT-style context staging

Summary of Decisions (for Replit alignment)
	•	✅ OAuth redirect allowed, initiated inline
	•	✅ Inline attachment-specific errors, toast for global failures
	•	✅ Soft attachment limits (1 Figma, 3 images)
	•	✅ Quick actions stay visible but disabled when appropriate
	•	✅ Two-phase Figma fetch:
	•	Light metadata pre-Send
	•	Full analysis post-Send
