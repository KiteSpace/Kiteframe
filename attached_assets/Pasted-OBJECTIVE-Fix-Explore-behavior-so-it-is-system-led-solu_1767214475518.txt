OBJECTIVE

Fix Explore behavior so it is:
	•	system-led
	•	solution-oriented
	•	decisive
	•	low-cognitive-load

Explore must not behave like a generic Experiment.
This is a v1 fix that enforces intent without introducing new node types.

⸻

CORE CONSTRAINTS (NON-NEGOTIABLE)
	1.	Explore MUST NOT expose Experiment mode selection UI
	2.	Explore MUST propose concrete solutions, not abstract ideas
	3.	Explore MUST recommend a primary solution
	4.	Explore MUST limit options (max 2 total)
	5.	Explore MUST provide a clear default forward action
	6.	Explore remains an Experiment node internally (no new object type in v1)

⸻

PART 1 — LOCK EXPLORE MODE (CRITICAL)

Current issue:
Explore creates an Experiment node that still shows the mode selector (What If / Enhancement / Open).

REQUIRED CHANGE:

When an Experiment node is created via Explore (from an Insight):
	•	Hide the mode selector entirely
	•	Force the mode to explorationContext.suggestedMode
	•	Do NOT allow the user to change modes

Implementation notes:
	•	Add an origin: 'explore' | 'experiment' flag to ExperimentNodeData (or equivalent)
	•	In ExperimentNode.tsx, conditionally render the mode selector ONLY when origin === 'experiment'
	•	For origin === 'explore', the header must NOT show mode controls

Result:
Explore does not ask the user how to think about the problem.

⸻

PART 2 — DISTINCT EXPLORE AI PROMPT (QUALITY FIX)

Current issue:
Explore uses the same Experiment prompt with prefilled context, resulting in vague output.

REQUIRED CHANGE:

Introduce a distinct Explore prompt template (do NOT reuse Experiment prompt).

Explore prompt MUST instruct the AI to:
	•	Propose 1–2 concrete solution paths
	•	Clearly mark one solution as RECOMMENDED
	•	Describe explicit workflow changes (nodes, branches, conditions)
	•	Avoid abstract language (“improve UX”, “add validation”)
	•	Avoid questions and hedging

Required characteristics:
	•	Solution-oriented
	•	Assertive tone
	•	Actionable structure

Do NOT:
	•	Ask the user follow-up questions
	•	Present unbounded lists
	•	Frame output as brainstorming

⸻

PART 3 — LIMIT & PRIORITIZE SUGGESTIONS (ANTI-STUNLOCK)

REQUIRED RULES FOR EXPLORE OUTPUT:
	•	Minimum: 1 solution
	•	Maximum: 2 solutions total
	•	Exactly 1 solution MUST be labeled Recommended
	•	If only 1 solution is returned, it is implicitly recommended

Enforcement:
	•	Cap output at the prompt level
	•	Do NOT rely on UI truncation alone

Visual/UI rule:
	•	Recommended solution must have higher visual prominence
	•	Alternative solution (if present) must be visually secondary

⸻

PART 4 — DEFAULT FORWARD ACTION (UX FIX)

Current issue:
Explore leaves the user without a clear next step.

REQUIRED CHANGE:

For Explore-initiated Experiment nodes, add a primary CTA:

Primary CTA:
	•	Apply Recommended

Secondary (optional):
	•	View Alternative (only if a second solution exists)

Do NOT add:
	•	Mode switching
	•	“What would you like to do?”
	•	Open-ended follow-ups

Apply Recommended behavior:
	•	Applies the recommended solution directly to the workflow
	•	Creates or modifies nodes/branches as described
	•	Advances the workflow without additional user decisions

⸻

PART 5 — VISUAL DIFFERENTIATION (NO LAYOUT FORK)

Layout:
	•	Keep Experiment and Explore layout the same

Styling:
	•	Explore must be visually distinct from Experiment
	•	Use a stronger, more directive accent (e.g. insight/warning family)
	•	Header should clearly read as system-initiated (e.g. “Explore Solutions”)

Purpose:
Users must be able to distinguish Explore vs Experiment at a glance.

⸻

PART 6 — NO CHAT INTEGRATION IN V1

Explicitly DO NOT implement in v1:
	•	Automatic KiteAI chat sessions from Explore
	•	Conversational follow-ups
	•	Freeform discussion affordances

Explore is proposal-driven, not conversational, in v1.

(Chat integration may be added in a future release as an explicit opt-in.)

⸻

PART 7 — ACCEPTANCE CRITERIA (MUST PASS)

Test A — Explore creation
	•	Insight → Explore creates an Experiment node
	•	Mode selector is NOT visible
	•	Suggested mode is locked

Test B — Output quality
	•	Explore proposes max 2 solutions
	•	One solution is clearly labeled Recommended
	•	Solutions describe concrete workflow changes

Test C — UX flow
	•	“Apply Recommended” is present and primary
	•	Clicking it advances the workflow immediately
	•	No additional decisions required

Test D — Cognitive load
	•	User is never asked how to explore
	•	User is never presented with >2 equal-weight options

FAIL CONDITIONS:
	•	Explore shows mode selector
	•	Explore output is abstract or vague
	•	More than 2 solutions shown
	•	No clear recommended path
	•	User is left without a default action

⸻

DESIGN INTENT (REFERENCE)

Experiment = “Help me think”
Explore = “Help me move”

If Explore feels like brainstorming, this implementation is incorrect.
