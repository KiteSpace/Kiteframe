SECTION 1 — IMPROVE FIGMA SEMANTIC MODEL (D)
============================================================

Goal
----
Make the semantic model richer but fully backward compatible.
We want to better represent:

- Screens (frames / sections) as high-level units
- Forms and grouped fields
- Primary vs secondary actions
- Navigation flows between screens
- Element "roles" (input, action, nav, context)

We DO NOT want:
- ML models, remote calls, or heavy inference.
- Breaking changes to existing code that reads figmaSemantic.

1.2 Heuristic Enrichment in extractFigmaSemanticMetadata
------------------------------------------------------------

File: client/src/lib/integration/figmaSemanticExtractor.ts

You already traverse the Figma node tree and populate:
- elements[]
- forms[]
- navigationTargets[]
- workflowGraph?

We want to enrich this in three small, deterministic ways:

A) ScreenType and StateType

Use simple heuristics:

- If frame name or heading text contains:
  - 'login', 'sign in', 'sign-in' → screenType = 'form'
  - 'settings', 'preferences'     → screenType = 'settings'
  - 'list', 'table', 'results'    → screenType = 'list'
  - 'success', 'done', 'complete' → stateType = 'success'
  - 'error', 'failed', 'oops'     → stateType = 'error'
  - 'empty' or 'no items'         → stateType = 'empty'

If nothing matches, leave as 'unknown' or undefined.

B) Primary / secondary action inference

- For each button-like element (already detected by isButtonLike):
  - If it has a strong fill color and larger size than other buttons on the same screen:
      → mark isPrimaryAction = true, role = 'action'
  - Other buttons on the same screen:
      → isSecondaryAction = true when appropriate.

- Populate metadata.primaryActionIds / secondaryActionIds using element IDs.

C) Grouping elements into forms

Using existing forms[] candidates:

- For each FigmaSemanticFormCandidate:
  - Ensure fieldIds contain only elements with role === 'input' (or controlType starting with text/email/password/search).
  - If a label element is directly adjacent or grouped with an input element:
      - assign the same groupId to both label and input.
  - If a heading appears inside a form section:
      - include its elementId in descriptionElementIds.

Keep heuristics simple and safe. If not sure, leave fields undefined.
NEVER throw or break extraction when heuristics fail.

------------------------------------------------------------
2.2 Mapping rules (per frame)
------------------------------------------------------------

Use the following mapping guidelines INSIDE buildWorkflowFromSemantic.
These are high-level rules; exact code is up to you but should respect intent.

1) Single-screen core flow

For a typical “Login Screen”:

- 1 annotation node: "Login Screen" (from frameName / main heading)
- 1 compound/form node:
  - data describing fields (email, password, etc.)
- 1 process node for main action:
  - label like "User taps Login"
- 0–N optional nodes:
  - "Forgot Password" navigation
  - "Create Account" link, etc.

2) Element → node mapping

- Elements with role === 'input' → part of a form node, NOT separate workflow steps by default.
- Elements with role === 'action' and isPrimaryAction → main process nodes.
- Elements with role === 'action' and isSecondaryAction → optional or branch nodes.
- Elements with role === 'navigation' → edges / branch nodes leading to other screens (for future cross-frame workflows).
- Elements with role === 'heading' → annotation/context nodes (not required in the primary flow, but can appear at the top).

3) Forms

- For each FigmaSemanticFormCandidate:
  - Create ONE form node per form (where appropriate).
  - Node label: e.g., "Login form" (from form name or frameName)
  - Node data: include a list of fields: { name, controlType, required? }

4) States

- If stateType is 'error' or 'success':
  - Create dedicated nodes representing those outcomes (e.g., "Error state shown", "Success confirmation").
  - Connect them as branch outputs from main action nodes.

Do NOT create nodes for decorative / layout-only elements or icons. If element.role === 'decorative', skip it.

------------------------------------------------------------
2.3 Layout strategy inside a generated workflow
------------------------------------------------------------

After building nodes and edges in logical order, apply a layout.

Use the existing Layout plugin (per your earlier assessment):

- If single-screen, prefer vertical layout:
    input/form node(s) at top,
    primary action next,
    result nodes below.

- If multi-step (summary or cross-screen):
    use vertical or simple hierarchical layout so edges flow top → bottom or left → right.

Call patterns (example):

  layoutPlugin.verticalFlow(generatedNodes, {
    align: 'center',
    spacingY: 120,
  });

Exact API may differ; use existing Layout utility functions.
The requirement is: DO NOT leave nodes unpositioned or randomly scattered.

SECTION 3 — WORKFLOW GENERATION MODES (C)
============================================================

Goal
----
Allow users to choose between:

1) summary      → simple, PM-level flows
2) detailed     → more granular Designer-level flows
3) ai_refined   → LLM-refined structure on top of semantic

Each mode uses the same underlying semantic data, but filters and structures differently.

------------------------------------------------------------
3.1 Extend WorkflowGenerationOptions
------------------------------------------------------------

Already defined in 2.1:

  export interface WorkflowGenerationOptions {
    mode: 'summary' | 'detailed' | 'ai_refined';
    maxSteps?: number;
  }

Recommended defaults:
- summary:    maxSteps ~ 7–10
- detailed:   maxSteps ~ 25–30
- ai_refined: maxSteps unlimited (AI decides, but we still cap at semantic level if huge)

------------------------------------------------------------
3.2 Mode behavior — Summary
------------------------------------------------------------

Summary mode should:

- Focus on:
  - primary action path(s)
  - core form(s)
  - primary success/failure states

- Drop:
  - secondary navigation links
  - decorative / contextual nodes
  - deeply nested UI-level elements

Implementation inside buildWorkflowFromSemantic:

- Filter elements:
  - Keep:
    - primaryActionIds
    - elements under forms
    - major headings
    - key state nodes
  - Ignore:
    - role === 'decorative'
    - isSecondaryAction-only actions (unless few elements)

- Build a linear-ish main flow:
  - "User sees [Screen]"
  - "User fills [Form]"
  - "User taps [Primary Action]"
  - "System validates"
  - "System shows [Success/Error]"

- Ensure output nodes ≤ maxSteps (drop least-important nodes if exceeding).

------------------------------------------------------------
3.3 Mode behavior — Detailed
------------------------------------------------------------

Detailed mode should:

- Include:
  - all form fields
  - secondary actions
  - explicit navigation branches
  - state details

- Only exclude:
  - decorative elements
  - extremely noisy duplicates

Implementation details:

- Use the full semantic.elements / forms / navigationTargets / workflowGraph.
- Group form fields into structured form nodes.
- Build explicit branches for:
  - secondary actions (e.g., "Forgot password")
  - state variations (error vs success)

Layout:
- Prefer hierarchical layout or a structured vertical flow with branching.

------------------------------------------------------------
3.4 Mode behavior — AI Refined
------------------------------------------------------------

ai_refined mode uses the semantic model as input to an LLM to refine the workflow structure.

IMPORTANT:
- This is OPTIONAL and should plug into your existing AI infrastructure only.
- It MUST be deterministic from the UI’s point of view: one user click → one AI call → one workflow.

High-level flow:

1) Take semantic (FigmaSemanticMetadata) and optionally the output of buildWorkflowFromSemantic in 'detailed' mode.
2) Send a structured prompt to the existing AI client (OpenAI) requesting:
   - an ordered list of steps
   - labeled nodes
   - edges between nodes
   - optional grouping into subflows

3) Convert AI output into Node[] + Edge[].

Constraints:
- Do NOT add new backend routes unless absolutely required.
- Reuse existing AI utilities that already talk to OpenAI.
- Keep token usage reasonable (only one call per generation).

If AI fails:
- Fall back to 'detailed' mode and show a non-blocking warning in the console.

SECTION 5 — HISTORY / UNDO BEHAVIOR
============================================================

Requirement
-----------
Workflow generation MUST be a single undoable action:

- Undo removes all generated workflow nodes and edges.
- It does NOT:
  - delete the Figma reference image node
  - affect pre-existing nodes.

Implementation
--------------

In workflow-editor.tsx (or wherever you manage history):

1) Immediately before applying buildWorkflowFromSemantic result:

   saveToHistory("Generate workflow from Figma");

   // or whatever your existing snapshot function is

2) Then inside a single synchronous block:
   - addNodes(generatedNodes)
   - addEdges(generatedEdges)
   - update any grouping metadata if needed

3) Do NOT interleave additional history saves in that block.

Acceptance:
- After generation, pressing Undo once returns the canvas to exactly the prior state.
