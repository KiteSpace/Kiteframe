Kiteframe – KiteAI “In-Project Chat” Stabilization Plan (Phase-by-Phase)
Goal: Prevent destructive/garbage workflow mutations (duplicate graphs, option-label spam, append-without-replace) and ship a safe, predictable in-project AI assistant.

Context (Observed Failure)
- User asked for guidance + “make adjustments”
- Intent resolver returned ambiguous → defaulted to MERGE
- System applied decision repair (UNLABELED_EDGES) → “Option A/B/C/D” labels
- Mutation applied as append/merge (not replace) → duplicate workflow rendered on canvas
- Feature flags were disabled (useFeatureFlags outside provider) → guardrails likely off

Non-Negotiable Launch Requirements
R1. In-project chat must default to ADVISE/ANALYZE mode (no structural changes unless explicitly requested).
R2. Structural mutations must never silently append an entire second canonical workflow onto the existing canvas.
R3. Any “full graph” mutation requires explicit user confirmation OR must be converted to non-destructive annotations.
R4. “Option A/B/C/D” must never appear as edge labels in user-visible workflows.
R5. FeatureFlagProvider must wrap ALL surfaces that use feature flags; no silent “all flags disabled” runtime state in production.
R6. Every mutation is undoable with a single undo step and is logged as a single atomic history entry.

PHASE 1 — Introduce Explicit AI Modes + UI Contract
Problem: “Adjustments” was interpreted as permission to generate a new full workflow.
Fix: Add explicit AI “mode” and enforce mutation policy per mode.

1.1 Add AI Mode enum (shared type)
- types/ai.ts:
  export type AiMode = "ADVISE" | "EDIT" | "GENERATE";
- Default mode for in-project chat: ADVISE.

1.2 Update in-project chat UI
- Add a mode selector (or a lightweight toggle) with clear labels:
  - “Suggest” (default) → ADVISE
  - “Apply changes” → EDIT (requires explicit toggle)
  - “Create new workflow” → GENERATE (only on blank canvas OR explicit “new workflow” flow)
- If user asks “make adjustments” while in ADVISE:
  UI prompt: “I can suggest edits, or apply them. Apply changes?” (one-click confirm)
  (No second confirmation needed after user chooses Apply.)

1.3 Update server/router task types
- aiRouter taskType must include mode context:
  taskType: "workflow_advise" | "workflow_edit" | "workflow_generate"
- Do NOT route in-project workflow tasks through “general_chat” without mode.

Acceptance (Phase 1)
- In ADVISE: no mutation API is called.
- In EDIT: mutation API may be called only after user explicitly chooses Apply changes.

PHASE 2 — Intent Resolution: Replace vs Merge vs Patch (Hard Guardrails)
Problem: Ambiguous → defaulted to MERGE. This is unsafe for full-graph outputs.
Fix: Add deterministic classification: PATCH, REPLACE, BRANCH; eliminate “merge-by-default” for full graphs.

2.1 Implement MutationIntent + Policy
- types/mutation.ts:
  export type MutationIntent = "PATCH" | "REPLACE" | "BRANCH" | "ADVISE_ONLY";

2.2 Add “Full Graph Payload” detector
In applyChatWorkflowMutation.ts (or shared helper):
- Inputs: currentGraph, incomingMutationGraph
- Heuristics (use at least 3):
  H1: incoming nodes >= min(8, 0.6 * current nodes) OR incoming nodes >= 10
  H2: incoming contains >= 3 duplicate canonical labels present in current (e.g., Opportunity Identification, Build, Release)
  H3: incoming has a near-linear chain covering start→end steps (input→output) resembling complete workflow
  H4: incoming node ids are mostly new, with no stable mapping to existing ids

Return: isFullGraph = true/false.

2.3 Change ambiguous handling
- If isFullGraph === true:
  - resolvedIntent MUST NOT be “merge”
  - resolvedIntent becomes:
    - If mode === EDIT and user confirmed “Replace existing”: REPLACE
    - Else: ADVISE_ONLY (or require confirmation UI)
- If isFullGraph === false:
  - allow PATCH merge logic (small changes)

2.4 Remove implicit attachmentTarget behavior for full graphs
- If isFullGraph and intent != REPLACE:
  - do NOT attach/anchor; do NOT mutate; return “needs confirmation.”

Acceptance (Phase 2)
- The repro sequence never appends a second canonical workflow.
- Full-graph payload without explicit replace yields no canvas mutation.

PHASE 3 — Semantic Identity + Diff-based Editing (Stop Duplicates)
Problem: Even in PATCH mode, the system can duplicate nodes because it lacks semantic identity matching.
Fix: Add stable “semantic keys” and diff existing nodes rather than re-adding.

3.1 Add semanticKey to nodes
- For workflow nodes created by AI, compute:
  semanticKey = normalize(label) + ":" + normalize(type)
  Example: "opportunity-identification:input"
- Store in node.data.meta.semanticKey.

3.2 Matching algorithm (EDIT/PATCH)
When incoming node has semanticKey matching existing:
- Update existing node (label/description/icon) rather than creating a new node.
- Maintain existing node id and position unless explicitly requested to reposition.

3.3 Conflict resolution
If multiple existing nodes match same semanticKey:
- Prefer the one in the main path (highest betweenness / connectedness) OR earliest createdAt.
- Mark duplicates for cleanup suggestion (but do not auto-delete unless user confirms).

Acceptance (Phase 3)
- “Make adjustments” updates descriptions/labels on existing nodes.
- No duplicate “Opportunity Identification” nodes appear after an edit.

PHASE 4 — Decision Repair: Ban “Option A/B/C/D” and Require Meaningful Edge Labels
Problem: Decision repair created placeholder labels and polluted the canvas.
Fix: Replace placeholder edge labels with either:
- Empty labels (preferred), or
- Semantically derived labels (Yes/No, Met/Not Met, Sufficient/Insufficient), but ONLY when confident.

4.1 In runWorkflowRepairs.ts:
- For repairedIssueTypes: decision:UNLABELED_EDGES
- Remove default “Option A/B/C/D”
- New behavior:
  - If condition node label includes “?”:
    - Try derive from outgoing targets or node label keywords:
      Examples:
        “Criteria Met?” → “Met” / “Not met”
        “Detail Check” → “Sufficient detail” / “Insufficient detail”
    - Only apply if confidence >= 0.75; else leave unlabeled.
  - Never emit “Option *” strings.

4.2 Add lint/test
- Unit test: assert no edge.label matches /^Option\s+[A-D]$/i in any mutated workflow.

Acceptance (Phase 4)
- Repro run yields no “Option A/B/C/D” edges.
- Decision nodes may have unlabeled edges; that is acceptable.

PHASE 5 — Replace Workflow Operation (Atomic + Undo + History)
Problem: Even when replacement is correct, it must be atomic and reversible.
Fix: Add explicit replace operation that:
- Clears existing canvas nodes/edges (within that workflow tab)
- Inserts new graph
- Creates a single history entry
- Supports single undo

5.1 Implement replace operation
- workflow-editor.tsx or state layer:
  applyWorkflowReplace(newGraph):
    - snapshot old graph
    - set nodes = newNodes; edges = newEdges; objects preserved as configured (decide policy)
    - push history entry “Replace workflow via KiteAI”
    - ensure undo restores old snapshot

5.2 UX confirmation copy
- If AI proposes full-graph replace:
  “KiteAI is proposing a full workflow rewrite. Replace current workflow? (Replace / Cancel)”
- Include “Replace (undoable)” text.

Acceptance (Phase 5)
- Replace always results in exactly one canonical workflow on canvas.
- Undo returns to the prior state in one step.

PHASE 6 — Feature Flags + Safe Defaults (Stop Running Without Guardrails)
Problem: Feature flags disabled likely bypassed protections.
Fix: Ensure flags always available; define safe defaults.

6.1 Fix provider wiring (root + portals)
- main.tsx: wrap App with FeatureFlagProvider
- Any additional createRoot mounts (modals/overlays/panels): wrap them too
- Ensure in-project chat is inside provider.

6.2 Add “hard-safe” defaults in code (not flags)
Guardrails that must never be disabled by flags:
- full-graph append prevention
- option label ban
- replace confirmation requirement (unless blank canvas)
These should be core logic, not feature-flagged.

Acceptance (Phase 6)
- No FeatureFlags warning in prod/dev.
- Guardrails remain active even if flags fetch fails.
