01

Summary

This is what the reader is for: body copy at 15px on a 400px measure with 1.7 leading, which is roughly 60–70 characters per line. Long-form text is legible here in a way it never is in a 400px rail column at 13px.

Everything in this pane — the measure, the nav, the resize behavior — exists to protect that one property. If you port this and the body ends up at rail typography, delete the pane and save the work.

02

Background

Lists are the most common thing generated markdown gets wrong, so they are worth checking explicitly:

  • Generated markdown produces loose lists, meaning each item's content is wrapped in a paragraph tag.

  • With list-style-position: inside the marker renders on its own line and the text drops beneath it.

  • list-outside plus li > p { margin: 0 } is the two-line fix. Both are in this file.

Requirements

Per-section actions appear on hover or keyboard focus, so they never compete with the text at rest.

  • Four actions, not six. Suggest · Refine · Elaborate · Add examples fit the width and cover the real cases.

  • No Reset. It is undo wearing a different hat — version recovery in the header already does that job.

  • Autosave, no Save button. The header shows state; every regenerate snapshots the prior version.

why three steps?

Not every long response is a document, so not every long response should become a card. This is the other case: reasoning, explanation, an answer that belongs in the conversation.

Those get clamped instead — about twelve lines, a fade, and a toggle. The thread stays scannable, and nothing is hidden behind a click you didn't expect.

The distinction should be driven by the task that produced the response, not by counting words. A document-generating task always yields a card; ordinary conversation never does. Word-count and heading-count heuristics both sound reasonable and are untestable in practice — you end up with a card for a long answer and a wall of text for a short document.

Deciding by task type also means the card's metadata is real. You know the section count and the title because the generator produced them, rather than inferring them from the rendered markdown after the fact.
