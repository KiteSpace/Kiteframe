Onboarding flow

12 sections · 1,840 words · draft · updated Aug 18, 2:14 PM

01

Summary

New accounts reach an empty workspace with no obvious first action. Roughly 40% never create a first project, and of those who do, most arrive via the sample template rather than the create flow.

This document proposes a three-step guided start that produces a real project rather than a tour, on the argument that the fastest route to retention is owning something.

02

Problem

The empty state is honest but inert. It describes what a project is without giving a reason to make one, and the primary action competes with four secondary ones of equal visual weight.

  • No default path — every option is presented as equally likely.

  • The sample template is the most-clicked element, which suggests people want something populated, not instruction.

  • Invited users see the same empty state as solo signups, despite arriving with a project already in hand.

This list renders correctly because of list-outside plus li > p { margin: 0 } — the Phase A1 fix. In production today these markers sit on their own line above the text.

03

Goals

Move first-project creation from 60% to 80% of new accounts within the first session, without adding a modal tour.

Open question

Is "first project created" the right success metric, or is it "returned on day two"? These pull in different directions — a guided start optimises the first, a populated sample optimises the second.

✦Suggested rewrite

Move first-project creation from 60% to 80% of new accounts within the first session, measured on projects that still exist at day seven — so the metric cannot be satisfied by a project created and abandoned inside the flow itself.

Secondary: invited users skip the guided start entirely and land in the project they were invited to, which should raise their day-two return independently.

04

Requirements

Three steps, each producing a durable artifact rather than a dismissible overlay.

  • Name the work. One field, prefilled from the signup context where one exists.

  • Pick a shape. Three starting structures, not a blank canvas and not a gallery of twenty.

  • Land in it. The flow ends inside the created project with the first node selected.

Each step is skippable, and skipping all three produces the same empty workspace that exists today — the flow is additive, so it cannot regress the current path.

05

Edge cases

Needs content

Invited users, SSO signups where the org already has projects, and accounts that abandon mid-flow are all unaddressed. The amber dot in the contents nav marks sections in this state.

06

Out of scope

Team invitations, billing, and the template gallery. Each is a plausible next step and none of them is required to test whether a guided start moves the number.

yes

Here's the reasoning behind the three-step structure, since you asked me to explain rather than just write it.

The dominant failure in the current empty state isn't that people don't understand what a project is — it's that nothing in the interface expresses a preference. Five actions of equal weight is the same as no recommendation, and a new user with no recommendation defaults to the lowest-commitment option, which is the sample template.

A guided start works by removing that symmetry. One path is obviously the path, and the others remain available but visually subordinate. That's the whole mechanism — it isn't education, it's a default.

The reason each step must produce a durable artifact is retention: a tour can be dismissed and leaves nothing behind, so a user who abandons it is exactly where they started. A flow that has already named the project and picked a structure has produced something the user now owns, and ownership is what brings people back on day two.

The risk is that three steps is two too many for someone who knows what they want, which is why every step skips and skipping all three lands you in today's empty workspace.
