SECTION 1 — FIX FILE-LEVEL IMPORT (Figma 400 "Request too large")
================================================================================

Problem
-------
Current FILE imports (links without node-id) fail with:
  { "status": 400, "err": "Request too large. If applicable, filter by query params." }

This happens because:
  GET /v1/files/{fileKey}  (no query params) can be too large for complex files.

Required Fix
------------
Use Figma's depth parameter to limit the file response:

  GET /v1/files/{fileKey}?depth=1

This returns high-level page/frame structure without full deep node trees.

Step 1 — Update fetchFigmaFile
------------------------------

File: client/src/lib/integration/figmaApi.ts

1) Locate the existing fetchFigmaFile function. It likely looks similar to:

   export async function fetchFigmaFile(fileKey: string, patToken?: string) {
     return callFigmaApi(`files/${fileKey}`, patToken);
   }

2) Change it to:

   export async function fetchFigmaFile(
     fileKey: string,
     patToken?: string,
     depth: number = 1
   ) {
     // Use depth=1 by default to avoid "Request too large" errors on big files.
     return callFigmaApi(`files/${fileKey}?depth=${depth}`, patToken);
   }

3) Update all call sites to pass only (fileKey, token) OR (fileKey) and rely on the default depth=1.

   - In FigmaImportModal.tsx wherever fetchFigmaFile is called, do NOT pass an explicit depth,
     unless you intentionally want deeper hierarchy (rare).

Step 2 — Graceful Error Handling for FILE Imports
-------------------------------------------------

File: client/src/components/modals/FigmaImportModal.tsx

In the logic that handles FILE URLs (no nodeId), you already have something like:

   try {
     const fileData = await fetchFigmaFile(parsed.fileKey, tokenToUse);
     const discovered = discoverFrames(fileData);
     ...
   } catch (error) {
     console.error("Figma import error:", error);
     // show error message to user
   }

With depth=1, the 400 "Request too large" case should be resolved for most files.
No further change is required here, beyond using the new fetchFigmaFile signature.

SECTION 2 — CONFIRM URL TYPE HANDLING (FRAME / PAGE / FILE)
================================================================================

This section is mainly to confirm, not rewrite.

URL Detection
-------------

File: client/src/lib/integration/figmaUrl.ts

You already have detectFigmaUrlTypeWithNodeType(...) and detectFigmaUrlType(...).
Do NOT change their behavior if they already:

- Return 'frame' when node-id resolves to FRAME or SECTION-like frame
- Return 'page' when node-id resolves to CANVAS
- Return 'file' when no node-id is present
- Return null for invalid URLs

FigmaImportModal Step Routing
-----------------------------

File: client/src/components/modals/FigmaImportModal.tsx

Confirm the following behavior:

1) FRAME URL
   - Has nodeId AND node.type === FRAME or SECTION
   - Behavior:
     - NO multi-step options
     - Directly imports a single frame as an image node
     - Calls onImport with [frame] and mode: 'new-project' or 'current-project'
     - Does NOT generate workflows automatically

2) PAGE URL
   - Has nodeId AND node.type === CANVAS
   - Behavior:
     - Shows 'page-options' step
       - Option A: "Import as a single image"
       - Option B: "Select individual frames from this page"
     - If Option A selected:
         → Call images endpoint for the PAGE and create ONE flattened image node
     - If Option B selected:
         → Transition to 'frame-selection' with only frames from this page

3) FILE URL
   - No nodeId parameter present
   - Behavior:
     - Shows 'file-options' step:
       - Option A: "Select individual frames" (default)
       - Option B: "Import a page as a single image"
     - Option A:
         → Use fetchFigmaFile(fileKey, tokenToUse) (now depth=1)
         → discoverFrames(...) returns frames for all pages
         → Show FigmaFramePicker with frames grouped by page
     - Option B:
         → Show 'page-selection' step (list of pages)
         → User chooses a page
         → Use images endpoint to fetch a single flattened page image
         → Create ONE image node

If any of this behavior is missing or diverges, align it to the above.

SECTION 5 — LAYERS PANEL PROJECT-SCOPING CONFIRMATION
================================================================================

Objective
---------
Ensure that Layers panel state does NOT leak across projects and that workflow
grouping is recomputed per project correctly.

Stores to Verify
----------------

The following should all be project-scoped:

- collapseStore
- visibilityLockStore
- workflowNameStore
- nodeToWorkflowStore

Implementation Rules
--------------------

1) LocalStorage keys MUST include projectId:

   Examples:

   - "kiteframe-layers-collapse-${projectId}"
   - "kiteframe-layers-visibility-${projectId}"
   - "kiteframe-workflow-names-${projectId}"

2) There MUST be a function similar to:

   resetLayersState(projectId: string)

   That:
   - Clears in-memory Maps for:
       - collapse
       - visibility/lock
       - nodeToWorkflow
   - Reloads any persisted state from project-scoped localStorage keys
   - Triggers re-running of FlowDetection.detectFlows() for the current project's nodes/edges

3) On project change:

   In workflow-editor.tsx (or wherever the active project changes):

   - Call resetLayersState(activeProjectId) before rendering LayersPanel.
   - Pass projectId down into LayersPanel as a prop.

Acceptance Criteria
-------------------

- Switching between two projects with different workflows should NEVER show
  stale workflow groupings from the previous project.
- Collapsed/hidden states should be independent per project.

SECTION 6 — WORKFLOW GENERATOR: ENSURE METADATA USAGE AND BATCH UNDO
================================================================================

Objective
---------
Ensure that the workflow generator:

- ONLY runs when explicitly triggered (already true).
- Uses figmaSemantic metadata as its primary source (already mostly true).
- Produces a single coherent workflow group per generation.
- Is fully undoable in one step.

File: client/src/lib/kiteframe/semanticWorkflowGenerator.ts
File: client/src/pages/workflow-editor.tsx

Step 1 — Confirm semantic usage
--------------------------------

In semanticWorkflowGenerator.ts:

- It should read:
    const semantic = sourceImageNode.data?.figmaSemantic;
- It should access semantic.workflowGraph or equivalent.
- It should build nodes and edges using semantic.edges, semantic.elements, etc.

If any fallback logic exists that generates nodes with no semantic basis, it
should be removed or clearly guarded behind a flag.

Step 2 — Batch undo for generated workflows
-------------------------------------------

In workflow-editor.tsx, where "Generate Workflow" is invoked:

- Wrap all node/edge creation in a single undo batch:

  undoManager.batch(() => {
    // create new workflow nodes
    // create edges
    // update any workflow grouping metadata if needed
  }, "Generate workflow from Figma");

- Ensure that pressing Undo once removes ONLY the newly generated workflow
  nodes and edges, and does not affect:
    - Figma reference nodes
    - Other existing workflows

Step 3 — One workflow group per generation
------------------------------------------

- If your grouping system uses workflowGroupId or similar:
  - Assign a unique workflowGroupId to all nodes created in a single generation.
  - Edges must connect nodes within this group.
- Do not create multiple disjoint workflows from a single generation action
  unless explicitly required.

SECTION 7 — OPTIONAL BUT RECOMMENDED: SEMANTIC QUALITY IMPROVEMENTS
================================================================================

This section is OPTIONAL and should be implemented only after all prior sections
are complete and stable.

Goals
-----

- Improve quality of generated workflows from Figma semantic data.
- Reduce "messy" or orphan-heavy graphs.

Suggested Heuristics
--------------------

In semanticWorkflowGenerator.ts:

1) Deduplicate elements:
   - If two semantic elements map to the same visual or label, merge into one node.

2) Pair labels + inputs:
   - For a TEXT label immediately adjacent to an INPUT-like element,
     create a single "field" node with both label and name.

3) Ignore decorative sections:
   - Containers without interactive children should not become separate steps.

4) Filter out non-interactive icons:
   - Icons that do not represent actions should not map to workflow steps.

5) Simple layout:
   - After node creation, apply horizontal or vertical flow layout so that
     the resulting workflow is readable by default.

These are guidelines, not hard requirements. Keep initial implementation simple.
