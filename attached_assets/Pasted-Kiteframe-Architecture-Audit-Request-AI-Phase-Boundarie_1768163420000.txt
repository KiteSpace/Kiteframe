Kiteframe – Architecture Audit Request (AI Phase Boundaries)

Context
We are debugging structural issues in Kiteframe’s AI-driven workflow generation and mutation system. We do NOT want fixes or refactors yet. This request is for READ-ONLY ANALYSIS and DOCUMENTATION so we can re-evaluate phase boundaries, assumptions, and leakage between AI contexts.

Do NOT modify code.
Do NOT propose UX changes.
Do NOT implement anything.
Only inspect, trace, and document what exists today.

Deliverables Required
Please produce the following artifacts as Markdown documents.

------------------------------------------------------------
1. AI PHASE BOUNDARY MAP
------------------------------------------------------------

Identify all distinct AI “phases” or equivalent states in the codebase, whether explicit or implicit.

For EACH phase, document:
- Phase name (or inferred name)
- Entry conditions (what triggers this phase)
- Exit conditions (what transitions it to another phase)
- Primary files involved
- Allowed side effects
  - Can it mutate workflows?
  - Can it create projects?
  - Can it modify nodes/edges?
- Forbidden side effects (if any are enforced)
- Data contracts (what inputs/outputs are expected)
- Any assumptions the phase makes about:
  - project existence
  - workflow existence
  - canvas availability

Explicitly call out where boundaries between phases are unclear, overlapping, or leaky.

------------------------------------------------------------
2. PROMPT → ACTION TRACE (HOME vs IN-PROJECT)
------------------------------------------------------------

Trace the full execution path for:

A) Home / proposal flow (before a project exists)
- User submits prompt on homepage
- AI generates initial workflow concept
- User selects follow-up options (e.g. include edge/fail cases)
- AI attempts to update the proposal

B) In-project AI flow (after a workflow exists)
- User sends message in KiteAI chat
- AI produces suggestions or workflow output
- System decides whether to mutate the workflow

For EACH flow:
- List functions invoked in order
- List files involved
- Identify decision points (intent resolution, merge/replace, confidence thresholds)
- Identify where side effects occur
- Identify where mutation code is reachable
- Identify where failures can silently no-op

------------------------------------------------------------
3. WORKFLOW MUTATION ENTRY POINT INVENTORY
------------------------------------------------------------

List EVERY function that can mutate:
- workflows
- nodes
- edges
- canvas state
- history state

For EACH mutation entry point:
- File + function name
- What calls it
- What assumptions it makes (e.g. workflowId exists)
- Whether it supports:
  - patch edits
  - full replacement
  - appends
- Whether it performs:
  - clearing of nodes/edges
  - semantic matching
  - decision repair
- Whether it is gated by explicit user confirmation

------------------------------------------------------------
4. AI PROMPT REGISTRY
------------------------------------------------------------

Extract all AI prompts and prompt templates used in the system, including:
- System prompts
- Task-type prompts (general_chat, workflow_reasoning, etc.)
- Any reasoning vs execution variants

For EACH prompt:
- File location
- Intended phase (home proposal, in-project edit, etc.)
- Expected output format (JSON, text, mixed)
- Whether the code ENFORCES that format
- Whether the prompt implies mutation or proposal behavior

------------------------------------------------------------
5. PHASE COUPLING & LEAKAGE REPORT
------------------------------------------------------------

Identify and document:
- Helpers or utilities shared across multiple AI phases
- State objects reused across phases
- Logic that runs in both home and in-project contexts
- Any places where proposal logic can reach mutation logic

Explicitly flag high-risk coupling that could cause:
- unintended canvas mutations
- orphaned nodes
- topology loss
- silent failures

------------------------------------------------------------
Output Format Requirements
------------------------------------------------------------

- One Markdown document per section (1–5)
- Clear headings and bullet points
- No speculative fixes
- No redesign suggestions
- No code changes

Goal
This audit will be used to:
- Re-evaluate AI phase boundaries (PLAN / ADOPT / BUILD)
- Decide whether visible mode toggles are necessary
- Identify where an explicit “adoption phase” is missing or collapsed

Please confirm once the audit documents are ready.

End of request.
