KITEFRAME — PM-LEVEL REASONING HARDENING
Unified Replit Instructions (.txt)
Scope: Phase 3.5 — AI Quality & Reasoning Enforcement
Owner: KiteAI (PreProjectChat + Workflow Generation)

============================================================
GOAL
============================================================

Prevent shallow, checklist-style workflows from being generated
even when they technically pass existing structure + confidence
guards.

The AI must PROVE it is reasoning like a Product Manager, not
summarizing topics.

This is achieved by:
1) Adding PM Depth Guards (code-level enforcement)
2) Replacing the PM system prompt with a proof-obligation version

No UI changes required for this phase.

============================================================
PART 1 — PM DEPTH GUARDS (CODE-LEVEL)
============================================================

Problem:
Current guards ensure a workflow is valid, but not meaningful.
Shallow outlines can still pass execution-ready.

Solution:
Add a new guard that enforces PRODUCT DECISION DEPTH.

------------------------------------------------------------
A. NEW GUARD: assertPMDepth()
------------------------------------------------------------

Create a new guard file:

client/src/ai/guards/pmDepthGuards.ts

------------------------------------------------------------
B. PM DEPTH DEFINITION
------------------------------------------------------------

A workflow is considered PM-DEPTH-SUFFICIENT if it includes
AT LEAST ONE of the following:

1. Explicit Tradeoff
   - Competing approaches (e.g. friction vs speed)
   - Business vs UX tension
   - Accuracy vs conversion, automation vs control

2. Conditional Outcomes with Consequences
   - Branches that materially change user state
   - Not just "retry" or "error → back"

3. Risk-Driven Decision
   - Fraud, churn, drop-off, abuse, misconfiguration
   - Explicit mitigation steps

4. Irreversible Decision Point
   - Commitments that cannot be undone in-flow
   - e.g. account creation, data submission, pricing lock-in

------------------------------------------------------------
C. IMPLEMENTATION DETAILS
------------------------------------------------------------

Function signature:

assertPMDepth({
  semanticWorkflow,
  role,
  confidence
}): void

Only applies when:
- role === 'pm' OR role === 'hybrid'
- confidence >= 0.7 (otherwise handled earlier)

------------------------------------------------------------
D. HOW TO DETECT DEPTH (HEURISTICS)
------------------------------------------------------------

Use semanticWorkflow content (already available):

Check for keywords / signals such as:
- "tradeoff", "vs", "option A / option B"
- "risk", "failure", "mitigation"
- multiple decision nodes with distinct outcomes
- conditional language: "if", "otherwise", "depending on"

Pseudo-logic:

const hasTradeoff = detectTradeoff(semanticWorkflow)
const hasRisk = detectRisk(semanticWorkflow)
const hasIrreversibleDecision = detectIrreversible(semanticWorkflow)
const hasMeaningfulBranching = detectNonRetryBranches(semanticWorkflow)

if none are true → FAIL

------------------------------------------------------------
E. FAILURE BEHAVIOR
------------------------------------------------------------

If assertPMDepth fails:

- DO NOT allow execution-ready
- Force state back to:
  CLARIFICATION or ESCALATION
- Provide a single explanation:

"⚠️ This workflow is structurally valid but lacks
meaningful product decisions. Clarification required."

------------------------------------------------------------
F. WHERE TO CALL THIS GUARD
------------------------------------------------------------

Add assertPMDepth() in:

client/src/ai/guards/workflowGuards.ts

Call it AFTER:
- assertPromptActionable()
- assertWorkflowStructure()

But BEFORE:
- project creation
- preview → commit transition

PART 2 — PM SYSTEM PROMPT V2 (PROOF OBLIGATIONS)
============================================================

Problem:
Current PM system prompt describes behavior, but does not
require the model to PROVE reasoning depth.

Solution:
Replace PM system prompt with a PROOF-OBLIGATION prompt.

------------------------------------------------------------
A. FILE TO MODIFY
------------------------------------------------------------

client/src/ai/prompts/system.pm.txt

------------------------------------------------------------
B. REPLACE CONTENT WITH THE FOLLOWING
------------------------------------------------------------

[BEGIN SYSTEM PROMPT — PM MODE V2]

You are acting as a SENIOR PRODUCT MANAGER.

Your job is NOT to be helpful.
Your job is to PREVENT poorly-defined products from being built.

You must enforce product thinking before execution.

--------------------------------------------------
NON-NEGOTIABLE RULES
--------------------------------------------------

1. Linear checklists are NOT workflows.
2. Summaries of topics are NOT workflows.
3. A workflow must represent DECISIONS, not categories.

--------------------------------------------------
PROOF OBLIGATIONS (MANDATORY)
--------------------------------------------------

Before generating ANY workflow structure, you must be able to
explicitly identify ALL of the following:

A. WHO
- The primary user
- At least one secondary or impacted stakeholder

B. GOAL
- The user’s concrete goal
- The business goal (they may conflict)

C. DECISIONS (REQUIRED)
You MUST identify at least THREE non-trivial decisions.
Each decision must include:
- The choice being made
- Why it matters
- What happens if it goes wrong

D. TRADEOFF (REQUIRED)
You MUST identify at least ONE explicit tradeoff, such as:
- Speed vs accuracy
- Friction vs conversion
- Automation vs control
If you cannot identify a tradeoff, STOP.

E. FAILURE MODE (REQUIRED)
You MUST identify at least ONE failure or misuse scenario
that materially alters the flow.

--------------------------------------------------
EXECUTION RULES
--------------------------------------------------

If ANY proof obligation above cannot be satisfied:

- DO NOT generate a workflow
- DO NOT suggest starting a project
- Respond ONLY with clarifying questions

If the user avoids answering twice:
- Propose 3 concrete options they can choose from
- Do NOT proceed until one is selected

--------------------------------------------------
OUTPUT EXPECTATIONS
--------------------------------------------------

When generating a workflow:
- Decisions must be explicit
- Branches must lead to meaningfully different outcomes
- Failure paths must change system or user state
- Avoid generic nodes like "Define X" unless justified

If you cannot meet these standards, you must refuse to proceed.

[END SYSTEM PROMPT — PM MODE V2]
