KITEFRAME — INTENT RESOLUTION & CHAT-FIRST CREATION
ARCHITECTURE QUESTIONS FOR REPLIT

Purpose:
These questions are required to understand Kiteframe’s current implementation
so we can safely introduce a chat-first, intent-resolution flow BEFORE project
creation (for prompts, Figma imports, and image uploads), without breaking
existing workflow, PRD, Layers, or AI systems.

==================================================
SECTION 1 — PROJECT CREATION LIFECYCLE (CRITICAL)
==================================================

1. Where is a new project actually instantiated?
   - File(s) responsible for:
     - Creating project UUID
     - Initializing canvas state
     - Creating default workflow group
   - Is this logic inside:
     - WorkflowEditor?
     - onImport handlers?
     - A project store / utility?

2. Is project creation currently coupled to any of the following?
   - Prompt → workflow generation
   - Figma import
   - Image upload
   - First node insertion

3. Can project creation be deferred without breaking:
   - Undo/redo
   - Layers state
   - PRD storage
   - AI context resolution

4. What is the minimum data required to create a project?
   - projectId only?
   - projectName?
   - initial nodes?
   - cloud sync metadata?

Goal: Confirm whether a “pre-project” state is safe to introduce.

==================================================
SECTION 2 — HOMEPAGE PROMPT GENERATOR
==================================================

5. Where does the homepage prompt-to-workflow generator live?
   - Confirm file path (e.g. AiWorkflowGenerator.tsx)
   - Is it mounted inside routing or the workflow editor?

6. Does the homepage generator currently:
   - Call aiClient.chat() directly?
   - Create nodes and edges immediately?
   - Create a project immediately?

7. Can this generator be refactored to return an intermediate result instead
   of mutating canvas state?
   Example:
     {
       confidence: number
       requiresClarification: boolean
       suggestedQuestions: string[]
       preview?: WorkflowPreview
     }

8. Is there an existing chat component or lightweight message UI that could
   be reused here (instead of creating a new one)?
