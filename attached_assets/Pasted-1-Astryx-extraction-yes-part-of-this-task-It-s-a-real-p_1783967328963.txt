1. Astryx extraction — yes, part of this task.
It's a real prerequisite, not a one-liner, so it should be its own explicit step at the front of Phase 3 (call it Phase 2.5): pull the 19 components out of DesignCanvasViewer.tsx into @/components/astryx/, one file per component or a sensible grouping, with a barrel index.ts. Do this extraction before wrapping any of them with useNode() — get them out and confirm they still render identically in the old viewer first, then wrap.
2. Naming — resolve now, not mid-phase:

AstryxSection — build new. It has no equivalent today, and it's the one component that's structurally different (container vs. leaf) so it shouldn't be forced out of an existing component. Simple flex-container div wrapping children, minimal props (direction, gap, padding) to start.
AstryxInput → use the existing AstryxTextInput name as-is. Don't rename or alias — just target the real name in the resolver map and the AI prompt. Renaming existing components for cosmetic consistency isn't worth touching working code for.

Revised starter five: AstryxCard, AstryxButton, AstryxText, AstryxTextInput, AstryxSection (new).
3. Old claimed designs in saved_projects — leave them on the old renderer, indefinitely.
Don't migrate. Migration means writing a translator from flat x/y JSON into a craft.js tree with invented containment/nesting that was never actually specified by that data — that's guesswork dressed up as a migration, not a real conversion. Leave DesignCanvasViewer alive specifically to keep serving these old records read-only from saved_projects, and don't delete it as part of this task (see Q4).
4. /designs/:id — detect and branch, don't break old links.
New route serves designs table records through DesignEditor. Old external_entities flat-JSON records keep resolving through the existing DesignCanvasViewer code path at whatever route currently serves them — don't consolidate these into one route with format-sniffing, since that adds branching complexity for records that are frozen and not gaining new capability anyway. Two routes/paths, old one left untouched, is simpler than one route with a version-detection branch. DesignCanvasViewer.tsx does not get deleted in this task — only its component definitions get extracted out to the shared barrel (Q1); the viewer itself keeps running for old links.
5. External route — new designs table, not external_entities.
Migrate the external/skill path to the new table. Reasoning: external_entities' validation schema was built for the old flat format — reusing it means either the new craft.js tree data gets force-fit into a schema that doesn't describe it, or you maintain two schemas for the same route. Since this route hasn't shipped a real design-generation skill yet (only the workflow skill exists so far), there's no live external consumer depending on the old shape — clean cutover, no migration debt.
6. Native entry point — split the tile, don't replace it.
NewTabTypePicker's "Design" option becomes two choices: "Generate with AI" (existing KiteAI flow, now targeting the new schema per Phase 6) and "Blank canvas" (opens DesignEditor on an empty native design via POST /api/designs). Don't make blank-canvas a separate top-level route users have to know to find — surface it right next to the AI option where people already look for "Design."
7. Good catch — confirm before starting.
Given @astryxdesign/core already failed silently on a peer-dep mismatch once, don't skip this. Run the dry-run install and confirm @craftjs/core resolves cleanly against React 18.3 before any Phase 3 work begins — cheap to check now, expensive to discover mid-build.
One meta-note: these answers shift the build order slightly — extraction (Q1) and the two naming resolutions (Q2) are now explicit Phase 2.5 work ahead of the original Phase 3, and the craft.js compatibility check (Q7) should happen at the very start, before Phase 2. Worth having Replit confirm the updated sequence back to you before they start, given how much got clarified here.
